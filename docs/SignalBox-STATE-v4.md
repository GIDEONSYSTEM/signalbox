## 0. Что это и куда движется

Утилита для студий подкастов: мониторинг и управление камерами по локальной сети. Один C++
процесс без окна: находит камеры, следит за их состоянием, поднимает HTTP-сервер на **:8787**
и отдаёт панель управления. Панель открывают в браузере, на телефоне или цепляют в OBS как
Custom Browser Dock.

🔴 **Программа многовендорная — это не «пульт для Sony».** Сегодня работают камеры **Sony** по
Wi-Fi (Sony Camera Remote SDK, PC Remote / PTP-IP), и добавляется **Blackmagic** по Ethernet
(их открытый REST API + WebSocket, §15). Замысел владельца — **единый пульт на всю студию**,
независимо от марки. Отсюда требования к решениям:
- вендор-специфичное прячется за общий интерфейс, а не растекается по коду — тот же приём,
  что с платформенным слоем (§14);
- **карточки в панели у разных марок РАЗНЫЕ** (решение владельца): показываем ровно то, что
  позволяет API конкретной камеры, и не натягиваем на неё чужую модель свойств — §15.8;
- «камера» в коде больше не равна «сессия Sony SDK»: у Sony состояние снимается опросом
  ~1/сек, у Blackmagic приходит подпиской (§15.5), а живого превью там нет вовсе (§15.7).

**Планы владельца (важно для решений):**
- 📹 **интеграция камер Blackmagic** — в студии три PYXIS 6K; разведка на живом железе
  проведена 2026-08-18, кода пока нет (§15);
- 💰 **программу будут продавать** — сейчас идёт бесплатное тестирование с несколькими студиями;
- 🔒 позже — лицензирование (см. §9);
- 🍎 позже — версия под **Mac Apple Silicon** (см. §9).

**Камеры, виденные в работе:** ZV-E1 (192.168.0.83, .129), ILME-FX30 (192.168.0.238).
Заявлялись также ZV-E10 II (`ZV-E10M2`) и FX3.
**Blackmagic:** три **PYXIS 6K** (прошивка 10.2, Ethernet, сеть `192.168.1.0/24`) — §15.0.

## 2. HTTP API (порт 8787, `INADDR_ANY`)

- `GET /status.json` → `{server, cameras:[{id,model,ip,online,rec,battery,acPower,cardMinutes,
  writing,iso,isoEff,aperture{cur,opts},shutter{cur,opts},wb{cur,opts},wbKelvin,micGain{cur,opts}}]}`
- `POST /cmd` → `{cam:N|"all", action, value}` **или** `{cams:["ip",…], action, value}` (группа одним
  запросом). `action`: `rec|iso|aperture|shutter|wb|wbkelvin|micgain`
- `GET /cameras.json` · `POST /cameras/add {ip,model,ssh}` · `POST /cameras/remove {ip}`
- `GET /groups.json` · `POST /groups/save` (схемой владеет панель, C++ только персистит).
  Тело: `{"groups":[…], "ungrouped":[ключи]}` — второй ключ хранит порядок карточек вне залов
  (§21.3); C++ читает только `groups`, лишние ключи проходят насквозь и возвращаются дословно
- `GET /cardlayout.json` · `POST /cardlayout/save` — что показывать в карточке и в каком порядке;
  тот же уклад, что с группами: схемой владеет панель, сервер только хранит (§20)
- `GET /update.json` · `POST /update/check` · `POST /update/install` · `POST /update/settings {auto}`
- `POST /restart` · `POST /shutdown`
- `GET /status.json?seq=N` → **304** без тела, если статус не менялся; версия в `X-Status-Seq` (§17.8)
- `GET /liveview/<n>.jpg?seq=N` → JPEG + заголовки `X-Cam-Frames`, `X-Cam-Seq`; **304** если кадр не менялся
- `GET /` панель · `GET /<file>` статика из `www\`

**Выбор LAN-адреса для `server`:** `GetAdaptersAddresses`; пропуск выключенных и loopback;
вес = `ipScore` −60 за виртуальный IfType (tunnel 131 / PPP 23 / propVirtual 53) +25 за настоящий
шлюз. Кандидаты и веса — в лог строками `[net]`.
⚠️ **Не определять адрес «маршрутом в интернет»** (UDP connect к 8.8.8.8): при VPN проба уходит
в туннель — проверено, выбирался `172.18.0.1` (xray_tun) вместо `192.168.0.176`.

## 3. Устройство процесса

**Без консоли.** `WIN32_EXECUTABLE TRUE` + `/ENTRY:mainCRTStartup` (Windows GUI, но обычный
`main()`). При старте сам открывает панель в браузере; при само-перезапуске получает `--restarted`
и вкладку не открывает. Весь `consolePrintf` → **`SignalBox.log`** рядом с exe (прошлый запуск →
`.log.prev`), открыт `_wfsopen(_SH_DENYNO)` + UTF-8 BOM.
⚠️ `[System.IO.File]::ReadAllText` лог на живой программе НЕ прочитает — читать `Get-Content`
или явным `FileShare.ReadWrite`.

**Значок в трее и главный поток.** `plat::runEventLoop()` (в слое): message-only окно
(`SignalBoxTrayWnd`, родитель `HWND_MESSAGE`) + `Shell_NotifyIconW`, меню — открыть панель /
перезапустить / выключить. Цикл просыпается раз в 150 мс и смотрит `g_running`.
🔴 **Цикл событий крутится на ГЛАВНОМ потоке, HTTP-сервер — в рабочем** (до 2026-08-10 было
наоборот). Причина: на macOS status bar item поднимается только с главного потока, иначе порт
пришлось бы выворачивать наизнанку.
⚠️ **Проверять значок через `FindWindow*` нельзя** — message-only окна так не находятся
(дважды получал ложное «нет»). Достоверно — строки лога `[tray] …`; пункты меню тестировать
посылкой `WM_COMMAND` с id в hwnd из лога.

**Единственный экземпляр.** Мьютекс `Local\SignalBox_SingleInstance`. Второй запуск открывает
панель работающего и выходит. Проверка стоит **до `openLogFile()`** (иначе второй экземпляр
затрёт лог живого); при `--restarted` ждёт до ~15с, а `relaunchSelf()` перед `CreateProcessW`
зовёт `releaseSingleInstance()` — без этого ломалась кнопка «Перезапустить».

**Сторож завершения.** `startShutdownWatchdog(8)` → через 8с `TerminateProcess`. Нужен потому,
что `poller.join()`/`discoverer.join()` могут висеть внутри блокирующего SDK `Connect()` к
несвязанной камере — так появлялись **зомби-процессы** (порт освобождён, процесс жив).
🔴 **Порядок в конце `main()` важен:** сначала дождаться потока сервера и закрыть сокет, и только
ПОТОМ заводить сторожа. Браузер держит открытые соединения, приём последнего запроса занимает
до 4с (`SO_RCVTIMEO`); пока это ожидание было внутри восьмисекундного окна, штатное выключение
не укладывалось и процесс каждый раз добивался принудительно (замерено: 8.2с и «затянулось»
против 1.0с и «Готово.»).

**Брандмауэр.** `maybeOfferFirewallRules()` через COM `INetFwPolicy2` ищет входящее Allow-правило
на свой exe; нет — MessageBox, при согласии `ShellExecuteExW("runas", "--firewall")` → UAC →
элевированный экземпляр добавляет TCP+UDP с `NET_FW_PROFILE2_ALL`. Отказ → `firewall-skip.txt`.
Ветка `--firewall` обрабатывается **до** single-instance-гарда.

**Перегрев (2026-08-13).** Камера сообщает его сама: `CrDeviceProperty_DeviceOverheatingState`
(`Int8Range`, значения из enum SDK — `0` норма, `1` близко к пределу, `2` перегрев). В
`status.json` поле `overheat` (`null` = камера свойство не отдаёт). Смена состояния пишется в лог,
чтобы потом можно было восстановить, когда началось.
- 🔴 **Оповещение на всю карточку бьёт УЖЕ ПРИ `1`.** Владелец грел камеру намеренно, и в логе
  видна вся последовательность: `нагрев близок к пределу` → `ПЕРЕГРЕВ` → `отключилась (0x8209)`.
  Между вторым и третьим — ничего: к моменту состояния `2` камера уже уходит в защиту, и
  предупреждать поздно. Ценность имеет ровно «вот-вот перегреется», пока оператор может успеть.
  Сначала порог стоял на `2` — это была ошибка, исправлена по живым данным.
- Заголовок оповещения зависит от состояния: `Высокая температура` при `1`, `Перегрев` при `2`.
  Карточку целиком накрывает затемнение с мигающим красным градусником и подписью
  «Нажмите, чтобы скрыть». Оповещение само ловит клик (оно поверх всей карточки), поэтому
  «нажать в любое место» получается без обработчика на карточке.
- **После скрытия** остаётся мигающий градусник в шапке — между остатком карты и кнопкой REC.
  Ухудшение (`1` → `2`) поднимает оповещение снова.
- Тепловые события пишутся в лог **со временем** (`plat::localTimeHms`) — без него «когда
  началось» по логу не восстановить, а именно это и спрашивают после сорванной съёмки.
- Оповещение всплывает на ПЕРЕХОДЕ вверх (`oh > предыдущего`), иначе, свернув его один раз,
  человек не увидел бы следующий случай. Возврат в норму сбрасывает «свёрнуто».
- ⚠️ **Проверено на живой ZV-E1: состояние реально доходило до `2`** после нескольких часов
  трансляции live view, потом само вернулось в норму. То есть свойство рабочее, а не декоративное.
  Вид оповещения проверялся подстановкой значений в `updateCard` — греть камеру намеренно незачем.

**Свойства камер:** статус `GetSelectDeviceProperties` ~1/сек; rec = `SendCommand(MovieRecord,
Down→Up)`; iso маска `& 0x00FFFFFF`, AUTO=`0xFFFFFF`; **кельвины — только `Colortemp`=0x0115**
(UInt16), НЕ `WhiteBalancePresetColorTemperature`(0x2A5); **микрофон — `AudioInputMasterLevel`**
(UInt16Range, у ZV-E1 диапазон 0..31 шаг 1, проверено на живой камере).

**MIDI:** зашитых привязок НЕТ. До 2026-08-13 здесь жил жёстко заданный тумблер на **CC #17** для
всех камер; с появлением привязок к группам он удалён по решению владельца — всё назначается в
настройках. Дебаунс 80мс и реакция только на нажатие (не на отпускание) остались.

**Горячие клавиши и MIDI на запись группы (2026-08-13).** В настройках раздел «Горячие клавиши»:
список существующих групп, у каждой можно назначить клавишу и/или кнопку MIDI-пульта. Нажатие —
**тумблер**: пишет хоть одна камера группы → останавливаем, иначе запускаем. Так одна кнопка
работает и на старт, и на стоп, и не занимает на пульте две.
- 🔴 **Клавиши регистрируются в СИСТЕМЕ** (`RegisterHotKey` / `RegisterEventHotKey`), а не ловятся
  хуком клавиатуры. Хук видит весь ввод в системе — на это ругаются антивирусы, и на macOS он
  требует разрешения «Мониторинг ввода». Плата за регистрацию: пока программа запущена,
  комбинация занята и до других приложений не доходит — в панели про это предупреждение.
- ⚠️ `RegisterHotKey` привязывает клавишу к очереди сообщений ПОТОКА, поэтому регистрация обязана
  идти из потока цикла событий; из HTTP-потока запрос маршалится `SendMessage` (синхронно — чтобы
  честно вернуть список занятых кем-то комбинаций). Обязателен `MOD_NOREPEAT`, иначе зажатая
  клавиша сыплет событиями и тумблер дёргается.
- 🔴 **Схемой `groups.json` по-прежнему владеет панель, но теперь сервер её ЧИТАЕТ:** MIDI приходит
  в C++, клавиши регистрируются там же.
- **Формат привязок (с 2026-08-13):** у группы массив `binds`, одна запись — ОДНА привязка:
  `{"action":"rec","key":"Ctrl+Alt+1"}` либо `{"action":"rec","midi":{"status":176,"d1":17}}`.
  Поэтому их можно назначать сколько угодно и удалять по отдельности, а поле `action` оставляет
  место будущим действиям: неизвестное сервер пропускает с сообщением в лог (`runAction`), а не
  ломается. Добавить действие = строка в `GROUP_ACTIONS` (панель) + ветка в `runAction` (сервер).
  Значение MIDI (`d2`) в привязке НЕ участвует: у кнопки нажатие и отпускание отличаются именно им.
- 🐞 **Миграция со старого формата обязана переписывать файл.** Сначала панель просто переносила
  старые поля `hotkey`/`midi` в `binds` в памяти — но сервер читает только `binds`, и уже
  назначенная кнопка молча переставала работать до ближайшего сохранения групп. Теперь
  `loadGroups`, встретив старый формат, сразу вызывает `saveGroups()`. Проверено на живом файле.
- ⚠️ **`loadGroups` обязан переносить `binds`**: `saveGroups` отправляет массив целиком, и поле,
  потерянное при загрузке, стёрлось бы при первом же сохранении.
- Обучение MIDI: `GET /midi/last` отдаёт последнее нажатие (`status`,`d1`,`d2`,`seq`), панель
  опрашивает его и ловит смену `seq`.
- Имена в разделе берутся из того же массива `groups`, что и залы на главном экране, а `renderKeys`
  вызывается из `renderGroups` — поэтому переименование зала сразу видно в настройках.
- **Проверено на Windows:** клавиша зарегистрирована системой, нажатие поймано при фокусе в
  браузере (то есть перехват действительно глобальный), группа найдена. Проверял на группе БЕЗ
  камер — чтобы не писать на карту.

⚠️ **ГРАБЛЯ:** `snprintf("%.4f")` на RU-локали печатает **запятую** → битый JSON. Числа
форматировать локале-независимо (`fx4()`).
🐞 2026-08-12: та же грабля нашлась ещё в двух местах — подписи выдержки (`0,8"` вместо `0.8"`)
и диафрагмы (`F2,8`). Там она JSON не ломала (значение внутри строки), но подпись зависела от
локали машины. Исправлено целочисленной арифметикой: десятые доли считаются в `unsigned`,
точка литеральная. **Правило: `%f` в этом проекте не использовать вообще.**

🔴 **КАМЕРА ПРИМЕНЯЕТ НЕ ТО ЗНАЧЕНИЕ, КОТОРОЕ ПРОСИЛИ** (найдено 2026-08-12 на живой ZV-E1).
SDK объявляет список выдержек ШИРЕ, чем камера поддерживает в текущем режиме: при 25/50p в
списке остаются «киношные» `1/48` и `1/96` (семейство 24p), которых на самом деле нет.
Камера применяет наше значение как **номер позиции в своём — более коротком — списке**, поэтому
промах равен числу таких «пустых» значений между текущим и запрошенным:

| Было | Просили | Получали | «Пустых» между |
|---|---|---|---|
| 1/60 | 1/50 | 1/50 ✅ | 0 |
| 1/40 | 1/50 | 1/60 | 1 (1/48) |
| 1/50 | 1/125 | 1/160 | 1 (1/96) |
| 1/160 | 1/50 | 1/40 | 2 (1/96, 1/48) |

Именно это выглядело как «поставил 1/50, а она прыгает на 1/40 и 1/60». Наша логика связи при
этом исправна — уходит одна команда с кодом из списка самой камеры.
**Лечение:** `CameraSession::reconcileLocked()` — после установки сверяем результат на следующем
опросе и досылаем команду (до `kSetRetries` = 3 раз, по одной на опрос ≈ 1 с). Сходится за
одну-две попытки: чем ближе, тем меньше «пустых» значений между. Если камера значение просто не
принимает (`1/48` при 25/50p), после трёх попыток отступаем и пишем в лог «больше не настаиваю» —
иначе программа спорила бы с человеком, крутящим колесо на тушке. Проверено на всех четырёх
случаях: теперь попадание точное, а отвергнутое значение не вызывает борьбы (12 с ровно).

## 4. Обнаружение камер — три пути

1. **Автопоиск** `EnumCameraObjects` (SSDP-мультикаст). Параметр `timeInSec` Sony документирует
   как **неподдерживаемый** — окно сканирования не увеличить.
2. **Ручные камеры — `cameras.txt`** (`IP МОДЕЛЬ [ssh]`), управляется из панели
   (Настройки → Камеры): `CreateCameraObjectInfoEthernetConnection` без перечисления.
3. **Автозапомненные — `cameras-known.txt`** (ведёт программа сама, `MAC IP МОДЕЛЬ`). Каждая
   найденная автопоиском камера туда пишется; если позже автопоиск её не увидит — подключаемся
   по сохранённому адресу. Смена IP по DHCP → поиск по MAC в `GetIpNetTable2`. Строгая ARP-проверка
   живости, иначе тихо пропускаем.

**Байт-порядок IP для SDK:** 1-й октет → биты 7..0 … 4-й → 31..24, т.е. `192.168.0.5 = 0x0500A8C0`
— ровно то, что даёт `inet_pton` в `S_un.S_addr`. Не менять на htonl.
**MAC не обязан быть настоящим** — по доке это лишь идентификатор объекта.

### 🔴 Почему камеры не находятся в чужой студии — РЕАЛЬНАЯ ПРИЧИНА

Находка коллеги: на роутере в **2.4 ГГц стояла ширина канала 20/40 МГц** — камера не находилась;
переключили на **20 МГц** — заработало. В студии владельца тоже 20/40, но там всё работает,
потому что помещение маленькое и эфир чистый.

Механизм: в 2.4 ГГц всего 3 непересекающихся канала, HT40 занимает полдиапазона; мощность
размазывается на вдвое широкую полосу (−3 дБ SNR), плюс при соседних сетях точка постоянно
дёргается 20↔40. Мультикаст не подтверждается и не переотправляется → отваливается первым,
unicast выживает за счёт ретраев. Отсюда «ping идёт, а камеры нет».

**Рекомендация (в `ЧИТАЙ-МЕНЯ.txt`):** 2.4 ГГц → строго **20 МГц**, канал вручную 1/6/11.
Прочие подозреваемые: фильтрация мультикаста на точке, IGMP snooping без querier, Wi-Fi в другой
подсети/VLAN, репитер.
⚠️ Моя гипотеза про профиль брандмауэра для ЭТОГО случая **не подтвердилась** — причина
оказалась радиочастотной. Спрашивать про ширину канала раньше, чем про брандмауэр.

## 6. Панель

`LV_BASE` = origin страницы (или `127.0.0.1:8787` для `file://`) → работает и с телефона.
**Порядок блоков:** шапка → «+ Группа» → группы → камеры без группы.
Всё конфигурационное переехало в окно настроек.

**Шапка:** слева логотип и **шестерёнка** (настройки); справа — метка «↑ версия» (если есть
обновление), квадратные кнопки-иконки перезагрузки и выключения, бейдж live.

**Окно настроек** (`#settings`): поверх панели, слева список разделов, справа содержимое —
как в OBS. Разделы: **Камеры** (добавление по IP), **Доступ** (адрес + QR), **Обновление**.
Закрывается крестиком, кликом по фону и Escape. Блоки туда **перенесены, не скопированы** —
иначе разъехались бы две версии одних настроек.

**Группы (съёмочные залы):** плиткой по ширине (`#groupsWrap` grid, `auto-fit`, колонка
ровно **392px** — с `1fr` растягивались в две карточки), внутри группы камеры **вертикально**,
всё центрировано. В шапке группы: треугольник сворачивания, имя (правится на месте),
**индикатор REC** (горит, только если пишут ВСЕ камеры; пустая группа не считается),
«Запись»/«Стоп», счётчик, ✕. Ниже ряд регуляторов ISO / Диафр. / Выдержка / ББ (±).
- **Свёрнутое состояние — в `localStorage`, НЕ на сервере**: каждый оператор сворачивает чужие
  залы у себя на телефоне, не влияя на док OBS и соседей.
- Перетаскивание карточек между группами (HTML5 DnD) + `<select>` «Группа» в карточке для тача.
- **Групповая запись — ОДИН запрос** `{cams:[…]}`, чтобы старт пришёлся на один проход; шаги
  ISO/диафрагмы/выдержки/ББ считаются **для каждой камеры от её значения** и уходят отдельными
  `/cmd` (не дублируем таблицы значений в C++).

**Карточка (раскладка 2026-08-12, с 2026-08-20 середина настраивается — §20):**
- **шапка одной строкой:** модель · батарея · молния питания · остаток карты · кнопка **REC**
  (прижата вправо). Бейджа STBY/REC больше нет — **кнопка сама и есть индикатор**: зелёная в
  ожидании, красная во время записи, надпись не меняется. «STOP» на красной кнопке читался бы
  как «остановлено», а не «идёт запись»;
- строка «Группа»;
- 🔴 **дальше — сетка параметров, которую задаёт оператор** (§20). До 2026-08-20 здесь были
  жёстко свёрстаны два ряда: «экспозиция» (ISO · Shutter · Aperture) и «звук и свет»
  (Mic Gain · WB) — теперь это лишь набор по умолчанию;
- Live Preview с рамками и поворотом.

**Что настраивается, а что нет.** Постоянны шапка, строка «Группа» и Live Preview: это
индикаторы, а не параметры. Настраивается ровно зона между «Группой» и превью.

Все регуляторы одного вида: подпись сверху по центру, под ней «− значение +», без рамок и
подложек. **Метрики (размер стрелок, поля значения, кегль и `line-height` подписи) заданы ОДИН
раз на все ряды** — когда они задавались по месту, ряды разъезжались по высоте на 4–11px.
🐞 С общей сеткой (§20) вылезло продолжение этой же истории: пока ряды жили в двух разных
контейнерах, разница высот была не видна, а в одной сетке соседние строки сразу разъехались —
ряд со списком 27.5px против 24px у ряда «− значение +» (замерено). Лечится там же, где и
остальные метрики: у `.ctl-row` своя `min-height:28px`, всё внутри по центру. Итог — **41.34px
у всех блоков обеих марок**, проверено измерением DOM. Подписи обязательно `white-space:nowrap`: «Mic Gain» из двух слов переносился
в узком блоке и ломал выравнивание.
**Mic Gain скрывается**, если камера уровень не отдаёт; контрол гаснет, если камера сообщила,
что свойство сейчас не пишется (поле `rw`, см. §10.0).

⚠️ **Как проверять вид карточки:** измерением DOM, а не на глаз, и с двумя оговорками, на которых
я споткнулся дважды подряд. У кнопки REC стоит `transition:.15s` — прочитанный сразу после смены
класса `getComputedStyle` отдаёт промежуточный кадр анимации; перед замером ставить
`style.transition='none'`. И опрос раз в секунду синхронизирует класс `.rec` с камерой, поэтому
навешенный вручную тестовый класс живёт меньше секунды — замер должен быть в том же
синхронном вызове.

**Модель камеры:** таблица `MODEL_NAMES` с **точным** совпадением + фолбэк «как есть, без
префикса ILME/ILCE/DSC/PXW/HXR». ⚠️ Раньше был поиск подстроки — `ILME-FX30` попадал под правило
`FX3`, и FX30 показывалась как FX3.

**Live Preview на весь экран (2026-08-12).** Кнопка в правом нижнем углу кадра (видна, только
когда кадр есть). В полноэкранном режиме доступны поворот, «Рамка глаза» и «Зона АФ» — эти органы
управления **ПЕРЕЕЗЖАЮТ** в панель поверх картинки и возвращаются в карточку при выходе. Копий не
делаем: два набора одних переключателей разошлись бы состоянием (тот же принцип, что с настройками
в §6). Выход — кнопкой или Escape (перехватывается в capture-фазе и гасится, иначе тем же нажатием
закрылось бы окно настроек под ним).
🔴 **Кадр на время режима переезжает в `<body>`.** Внутри карточки `position:fixed` считается не от
окна: у `.card` есть `transform`, а трансформация у предка делает `fixed` относительным к нему —
кадр раскрывался на 329×222 вместо 381×880 (поймано замером). Поэтому класс `fs` висит на самом
кадре, а не на разделе, и при удалении карточки (камера ушла в офлайн) обязателен `lvFsExit` —
иначе кадр остался бы висеть на экране без источника.

**Два уровня полноэкранного режима.** CSS-режим растягивает кадр на всё окно, а сверху
запрашивается **настоящий полноэкранный режим устройства** (`requestFullscreen`) — как у видео на
ютубе: без адресной строки и панелей браузера. На телефоне в альбомной ориентации без него
обвязка съедала половину экрана. Запрос возможен только из обработчика клика (нужен жест
пользователя), поэтому синтетическим кликом из консоли он НЕ проверяется — только руками.
Выход из режима устройства мимо нашей кнопки (жест, «назад», Escape) ловится через
`fullscreenchange` и сворачивает CSS-режим, иначе кадр остался бы растянутым поверх панели.
⚠️ **Safari на iPhone разворачивает так только `<video>`**, обычному элементу откажет — там
останется CSS-режим (кадр на всё окно, но с обвязкой браузера). На Android и на десктопе
работает полноценно.

**Live Preview:** искусственный потолок 7 к/с снят — частоту задаёт камера.
**Как это устроено целиком (три звена, частота, нагрузки) — §18.**
**Замер на живой ZV-E1: ~20 к/с**, кадр 12–42 КБ, 2–5 Мбит/с на превью. Чтобы однопоточный
сервер не захлебнулся, у кадров есть `seq`: клиент шлёт свой, сервер отвечает **304** без тела,
если кадр не менялся. Клиент опрашивает каждые 33 мс.
🐞 **До 2026-08-11 ветка 304 не срабатывала НИКОГДА:** сервер искал `seq=` в `req.path`, а строку
запроса `HttpServer` отрезает в `req.query` ещё при разборе — значит `haveSeq` всегда оставался
−1 и каждый кадр уходил целиком, даже неизменившийся. Панель при этом всё делала правильно
(`if(r.status === 304) return;`). После починки замерено: 60 запросов подряд каждые 20 мс →
**21 ответ 304 без тела**, 39 с кадром.
⚠️ **Как это проверять:** редкими запросами (раз в секунду) баг не виден — на живой камере кадр
успевает смениться, и 200 в ответ совершенно правилен. Нужны частые запросы и подсчёт кодов.
⚠️ **Браузер тормозит таймеры в фоновой вкладке** — в свёрнутом доке частота падает; это
поведение браузера, не наше. Мерить частоту только при видимой вкладке, иначе получишь чушь
(я получал «1 к/с» и «453 к/с»).

**QR:** библиотека **qrcode-generator** (MIT, `www/qrcode.js`), локально. Клик → крупный оверлей.
**Шрифты локальные** — внешний `<link>` на Google Fonts блокировал отрисовку (на телефоне с VPN
страница висела чёрной до тайм-аута).

## 7. Обновления через GitHub Releases

Репозиторий **`GIDEONSYSTEM/signalbox`** (публичный — только на время тестирования, см. §9).
Версия — `kAppVersion` в `main.cpp`; репозиторий — `kUpdateRepo` (пустая строка = проверка выключена).

**Как работает:** проверка при запуске и **раз в 4 часа** через **WinHTTP** (встроен в Windows):
`api.github.com/repos/<repo>/releases/latest` → `tag_name` + первый `.zip`-ассет → `cmpVersion`
почастно (чтобы 1.10 > 1.9). Панель показывает метку «↑ версия» в шапке и плашку в настройках.

**Установка без отдельного инсталлятора:** занятый exe и загруженные DLL не перезаписать, поэтому
архив качается в `%TEMP%\SignalBox-update\`, распаковывается встроенным **`tar.exe`**, затем
запускается распакованная копия с `--apply-update "<target>" <pid>` — она ждёт выхода старого
процесса, копирует **`robocopy`** (успех = код < 8) и стартует обновлённую программу.
Ветка `--apply-update` — **до** single-instance-гарда.

**Автообновление** — `settings.json` + галка «авто» в настройках, по умолчанию ВЫКЛ
(решение владельца: уведомление + кнопка, но с возможностью включить авто).

### Правила выпуска версии
1. поднять `kAppVersion` в `main.cpp` — это **единственное место**, где живёт версия;
2. собрать на каждой ОС и упаковать своим скриптом:
   - Windows: `powershell -ExecutionPolicy Bypass -File tools\pack-win.ps1`
   - macOS: `bash tools/pack-mac.sh`
   оба читают версию из `main.cpp`, кладут результат в `dist/` и **сами проверяют архив
   распаковкой** тем же инструментом, каким его распакует обновление;
3. синхронизировать три копии (§1);
4. на GitHub: Releases → Create a new release → **тег `vX.Y.Z`** → **приложить оба архива** → Publish
   (порядок загрузки значения не имеет, см. ниже).

🍎 **С 2026-08-11 в релизе ДВА архива** — под Windows и под macOS, с меткой ОС в имени
(`SignalBox-1.0.6-win.zip`, `SignalBox-1.0.6-mac.zip`). Выбор нужного при обновлении —
`src/UpdateAsset.h` (подробности в §14).

🔴 **ПОРЯДКОМ ВЛОЖЕНИЙ В РЕЛИЗЕ УПРАВЛЯТЬ НЕЛЬЗЯ — проверено на живом API.**
GitHub отдаёт `releases/latest` с вложениями, отсортированными **по имени файла**; порядок
загрузки не сохраняется вообще. Доказательство из релиза v1.0.6: виндовый архив был загружен
первым (`id=510576220`, 19:57:39), а в ответе API стоит **последним** — после `mac.pkg`
(`id=510576674`) и `mac.zip` (`id=510576693`), потому что «mac» < «win».
⚠️ Прежнее правило «виндовый архив заливать первым» держалось в этом файле один день и было
**неверным**: выведено рассуждением, а не проверкой. Классический случай на тему §10.4.

Практическое следствие: версии **по v1.0.5 включительно** берут первый `.zip` и в релизе с двумя
архивами всегда получат mac-сборку. Разрушительного ничего: 1.0.5 скачает архив, не найдёт внутри
`SignalBox\SignalBox.exe` и остановится с «архив распаковался неправильно», установка цела —
но и обновление не пройдёт.
**Решение владельца (2026-08-11):** порядок не подгонять и имена не уродовать. Коллегам на 1.0.5
архив 1.0.6 раздаётся напрямую, дальше они обновляются по метке сами. **Начиная с 1.0.6 порядок
вложений безразличен** — выбор идёт по метке ОС и покрыт тестом `tools/test-update-asset.cpp`.

🐞 **Метка ОС засчитывается, только если сразу после неё НЕ буква и не цифра** (точка, дефис,
подчёркивание или конец имени) — иначе `-mac` находился бы внутри `SignalBox-machine.zip`.
Практическое следствие, на котором легко обжечься:
`SignalBox-1.0.6-win.zip` ✅ → сборка для Windows,
`SignalBox-1.0.6-win64.zip` ❌ → **НЕ** считается виндовой, попадёт в «без метки» и будет
отдаваться обеим ОС. Релиз при этом выглядит совершенно нормально.

⚠️ **`tools/pack-win.ps1` обязан храниться в UTF-8 С BOM.** Windows PowerShell 5.1 без BOM читает
скрипт в ANSI, русский текст превращается в мусор, и парсер падает на «Unexpected token» там, где
ничего не сломано. Редактор, сохранивший без BOM, ломает скрипт молча.

⚠️ **Версия читается CMake на этапе КОНФИГУРАЦИИ.** Поэтому в `CMakeLists.txt` стоит
`CMAKE_CONFIGURE_DEPENDS` на `src/main.cpp` — без него правка `kAppVersion` запускает только
пересборку, `Info.plist` бандла хранит старую версию, и `pack-mac.sh` падает с «пересобери»,
хотя пересборка как раз не помогает (проверено на смене 1.0.5 → 1.0.6).

⚠️ **Тег обязан быть номером версии.** Первый релиз вышел с тегом `Minor` — `cmpVersion` счёл
его нулевой версией, и обновление молча «не находилось». Теперь панель пишет «тег релиза не
похож на версию».
⚠️ **Не забыть приложить архив.** Релиз `v1.0.3` опубликован без файла — обновление сломалось
у всех, программа честно сказала «в релизе нет архива .zip».
🐞 **Данные установки НЕ класть в архив.** Первый архив содержал `cameras.txt`, и обновление
затёрло бы список ручных камер студии. Исключать: `cameras.txt`, `cameras-known.txt`,
`groups.json`, `settings.json`, `cardlayout.json`, `firewall-skip.txt` — программа создаёт их сама.
Списки в `tools/pack-win.ps1` и `tools/pack-mac.sh` проверяют это перед упаковкой и падают,
если данные просочились: **заводя новый файл данных, добавлять его в оба списка.** `robocopy /E`
не удаляет лишнее в приёмнике, поэтому всё, чего НЕТ в архиве, обновление переживает.

## 9. Коммерческий контекст и планы (важно для решений)

**Программу будут продавать.** Сейчас — бесплатное тестирование с коллегами, поэтому репозиторий
публичный. **Перед продажами** нужно: закрыть репозиторий и переделать раздачу (публичные релизы
качает кто угодно).

**Про защиту честно:** программу, исполняющуюся на чужом компьютере, полностью защитить нельзя;
любой вшитый ключ извлекается. Цель — сделать копирование неудобным, а не невозможным.

**Рекомендованная архитектура лицензии** (обсуждена, не реализована): **файл лицензии с подписью**
— владелец подписывает своим закрытым ключом {студия, срок, привязка к железу}, программа
проверяет встроенным открытым ключом **офлайн**. Онлайн-проверка при каждом запуске не годится:
у продукта сквозное требование работать без интернета, и студия без сети окажется заблокирована
в разгар съёмки. Готовые платформы (Lemon Squeezy, Paddle) дают ключи и закрытые ссылки —
если брать их, обновления логичнее прицепить туда же.
**Совет по коду:** источник обновлений сделать абстрактным (манифест по настраиваемому адресу +
необязательный ключ), тогда переезд с GitHub на свой сервер или платформу — смена настройки.

**Mac Apple Silicon.** SDK Sony официально поддерживает macOS (отдельный пакет с их сайта;
есть ли нативная сборка под arm64 — по локальной доке не видно, смотреть на сайте Sony).
**Панель переносится без правок** — это чистый HTML. Логика камер переносима концептуально.
✅ **Платформенная обвязка вынесена в отдельный слой 2026-08-10 (см. §14)** — порт теперь
«написать одну реализацию `PlatformMac.mm`», а не распутывать Windows-вызовы по всему проекту.
Осталось выяснить по сайту Sony, есть ли нативная сборка SDK под arm64.

⚠️ **Юридическое:** перед продажами прочитать `Camera_Remote_SDK_Readme_v2.01.00.pdf` в корне SDK
— там условия Sony про распространение их DLL и коммерческое использование. Текст из PDF
извлечь не удалось (нет конвертера), читать глазами.
ℹ️ На Mac конвертер теперь есть — `pdftotext` из `poppler` (§15.2), так что эту читалку можно
не откладывать до Windows.

ℹ️ **У Blackmagic этой развязки нет:** управление идёт по открытому REST поверх HTTP, чужих
библиотек мы не линкуем и не распространяем (§15.9) — ни условий на редистрибуцию, ни возни с
подписью чужих бинарников. Зато появляется свой вопрос: **API камеры Blackmagic открыт всем в

продаж — разговор про изоляцию сети, а не про лицензию.

## 10. 🔴 Уроки методологии (читать до начала работы)

### 0. Правила работы с камерой (требование владельца, 2026-08-12)
Распространяются на **всё** управление камерами, без исключений.

1. **Ничего не выдумывать и не рисовать.** Списки ISO, выдержек, диафрагм, кельвинов, уровней
   микрофона — только те, что отдала САМА камера в этом ответе. Никаких зашитых таблиц, никаких
   «типовых» наборов, никакого округления к своим пресетам. Расхождение неизбежно: списки зависят
   от модели, режима, оптики и прошивки.
2. **Проверять, что изменение применилось.** Отправить команду мало — камера может применить
   другое значение или ничего. Читать результат и досылать, но с ограничением попыток, иначе
   программа спорит с человеком, крутящим колесо на тушке.
3. **Сверяться с докой SDK и сэмплами Sony.** Перед реализацией смотреть локальную доку (§13) и
   `RemoteCli/app/CameraDevice.cpp` + `SimpleCli`. Это уже окупилось: сэмпл перед установкой
   свойства проверяет `prop.IsSetEnableCurrentValue()` — можно ли его сейчас менять, — а мы этот
   флаг не читали и слали команды в пустоту (в режимах P/Auto выдержка не пишется).

1. **Свой энкодер нельзя валидировать своим декодером.** С QR я дважды отчитался об успехе на
   сломанном коде: round-trip сходился и RS-синдромы были нулевыми **потому что я считывал ровно
   то, что сам записал, в том же (неверном) порядке**. Нужен независимый декодер или живой сканер.
   Итог: самописный генератор выброшен, взята библиотека — подтверждено сканом с телефона.
2. **Не тестировать на живых данных юзера.** Дважды затирал его группы. Правильно: снять копию
   `groups.json` до теста и вернуть после; ещё лучше — проверять вычисленными стилями/DOM или
   подменять только ответ сервера в браузере, не мутируя данные.
3. **Синхронизировать три копии сразу** (§1) и напоминать про Ctrl+F5.
4. **Проверять фактами, а не рассуждением.** Гипотеза «профиль брандмауэра» звучала стройно,
   а реальной причиной оказалась ширина канала Wi-Fi. Возможности камеры выяснять дампом
   свойств с живой камеры, а не догадками по документации.
5. **Замеры делать в честных условиях.** Браузер в фоне режет таймеры; окно активности превью
   закрывается через 1.5с — из-за этого получал бессмысленные цифры, пока не померил со стороны
   сервера при открытом превью.

## 11. Грабли (must-know)

- Выключать только кнопкой на панели или из трея. Убийство процесса → камера отклоняет новое
  подключение (`0x820A`). Имя ПК для связывания: `WIN-T1I0U6MAIDA`.
- **`Настр. аутент. доступа` (SSH) на камере отключает «Связывание»** — при включённой
  аутентификации наш путь подключения не работает. Проверять первым делом.
- RU-локаль + `snprintf("%f")` → запятая → битый JSON.
- Рамки фокуса требуют `OSDImageMode=On` (HDMI при этом чистый).
- CAM-нумерация — по порядку обнаружения, между запусками перетасовывается. **Ключ камеры для
  групп — IP.** В `updateCard` обязателен `if(d.ip) e.ip = d.ip;` — иначе карточка сохранит IP
  прошлой камеры и уедет в чужую группу.
- POST_BUILD `copy_directory` может разово упасть сразу после линковки (антивирус держит свежий
  exe) — просто повторить сборку.
- `CrDevicePropertyCode` — **перечисление, а не namespace**: писать
  `SDK::CrDevicePropertyCode::CrDeviceProperty_X`, алиас `namespace P = …` не компилируется.
- Кнопки REC боевые: пишут на карты камер.

### 🐞 Обновление на macOS не работало вовсе — два бага (2026-08-17)

Найдено на живом обновлении **1.0.6 → 1.0.8**, которое запустил владелец. Симптом: программа
«думает», скачивает, гасит себя — и не запускается; версия прежняя. Установка обновления целиком
до этого не проходилась вживую ни на одной ОС (§12), поэтому оба бага дожили до релиза.

**1. Установщик не находил путь к цели, потому что искал кавычки.**
Уходящая копия зовёт `--apply-update "<цель>" <pid>`, а `applyUpdate` искал в командной строке
кавычку. На Windows `GetCommandLineW` отдаёт строку дословно и кавычки на месте; на macOS argv
плоский — `plat::launch` кавычки съедает при разборе, а `commandLine()` собирал строку обратно уже
без них. Итог: `q1 == npos` → `return 1`, установщик выходил мгновенно и молча.
Замерено на живом бинарнике, разница ровно в кавычках:
```
--apply-update /tmp/цель/SignalBox.app 99999    -> код 1, скопировано 0 файлов
--apply-update "/tmp/цель/SignalBox.app" 99999  -> код 0, скопировано 29 файлов
```
Починено с двух сторон: `applyUpdate` разбирает и строку без кавычек (pid — последнее слово, всё
до него цель; путь с пробелами так тоже разбирается), а macOS-`commandLine()` возвращает аргументы
с пробелами в кавычках. Кавычечная ветка осталась первой — **на Windows поведение не меняется**,
и старые копии 1.0.6/1.0.7, которые шлют строку по-прежнему, обслуживаются той же веткой.

**2. Обновлённая копия не запускалась: `/var` против `/private/var`.**
После починки №1 файлы копировались, но программа не поднималась. Причина: `exePath()` разрешает
путь через `realpath`, а `installRoot()` брал `bundlePath` у NSBundle как есть. Установщик работает
из `TMPDIR`, то есть из `/var/folders/…`, а `/var` — символическая ссылка на `/private/var`.
Префикс в `exeRelToInstall()` не совпадал, относительный путь молча превращался в абсолютный, и
запуск уходил по адресу вида `/Applications/SignalBox.app/private/var/…` — в никуда.
Воспроизведение однозначное:
```
установщик из /var/folders/… (TMPDIR)  -> файлы скопированы, копия НЕ запущена
установщик из /Users/…/sbstage         -> файлы скопированы, копия запущена
```
Починено: `installRoot()` на macOS тоже прогоняется через `realpath`.
⚠️ **Урок на будущее:** сравнивать пути на macOS можно, только приведя ОБА к `realpath`. Ловушка
не видна из папки без символических ссылок — а `TMPDIR`, `/tmp` и `/etc` все такие.

**3. Установленное из `.pkg` не могло обновиться: бандл принадлежит `root`.**
Пакеты macOS распаковываются от root, поэтому `/Applications/SignalBox.app` доставался
`root:wheel`. Обновление же работает от имени пользователя и копирует новый бандл поверх старого —
`rsync` упирался в `Permission denied`, `copyTree` возвращал false, `applyUpdate` молча выходил.
Именно на это налетел владелец: скачивание и распаковка проходили, версия не менялась.
```
ls -ld /Applications/SignalBox.app  ->  root:wheel
rsync -a <площадка>/ /Applications/SignalBox.app/  ->  Permission denied
```
Починено в установщике: `res/pkg-scripts/postinstall` отдаёт бандл пользователю, который ставил
(`chown -R`), скрипт подключается ключом `--scripts` в `tools/pack-mac-pkg.sh`.
⚠️ **Старые установки это не лечит.** Кто ставил `.pkg` версии 1.0.7 или раньше — у того бандл
по-прежнему root'овый, и обновление молча не пройдёт. Лечится переустановкой свежим `.pkg` либо
руками: `sudo chown -R "$(id -un)" /Applications/SignalBox.app`.
ℹ️ Установка из **zip** этой болезнью не страдает: пользователь распаковывает сам, владелец —
он же. Баг принесла именно `.pkg`-раздача.

**4. Обновлённая копия сразу выходила: установщик уносил с собой файл-замок.**
`acquireSingleInstance` держит `flock`, а на POSIX замок живёт при **описании открытого файла**,
которое переживает `fork`/`exec`. Установщик, запущенный уходящей копией, наследовал этот
дескриптор и держал замок, пока был жив. Свежая копия видела занятый слот и мгновенно выходила как
«второй экземпляр» — со стороны «обновилось, но не запустилось».
Замерено отдельно: при удерживаемом чужим процессом замке программа живёт секунды и гаснет, при
свободном работает.
Починено с двух сторон:
- `O_CLOEXEC` на файле-замке — течь закрыта в корне, но помогает только обновлениям **с 1.0.8 и
  выше**: старая копия всё равно передаст дескриптор;
- обновлённая копия запускается с **`--restarted`**, то есть ждёт слот до ~15 с. Установщик выходит
  сразу после запуска, слот освобождается — и это работает даже со старой копией. Заодно не
  открывается второй таб панели.

**5. Свежая копия блокировала сама себя унаследованным замком.**
После починок 3 и 4 обновление копировало файлы и запускало новую копию — а та жила ровно 15 секунд
и гасла, не написав даже своего лога (гард единственного экземпляра стоит ДО `openLogFile`).
`lsof` на файле-замке показал разгадку: на нём висели **два дескриптора одного и того же процесса**.
Замок ехал по цепочке `уходящая копия -> установщик -> свежая копия`, потому что `flock` держится
за описанием файла и переживает `exec`. Свежая копия открывала свой дескриптор, пыталась взять
`flock` — и упиралась в замок, который принесла с собой сама. Ждала 15 секунд (`--restarted`),
сдавалась, считала себя вторым экземпляром и выходила.
Починено в корне: `plat::launch` на macOS спавнит с **`POSIX_SPAWN_CLOEXEC_DEFAULT`**, то есть
потомок стартует с чистой таблицей дескрипторов (stdin/stdout/stderr оставлены явным `dup2` сам в
себя). Это закрывает весь класс: заодно перестали утекать слушающий сокет и открытый лог.
⚠️ Лечит обновления **с любой старой версии**, потому что `launch` вызывает установщик — то есть
НОВЫЙ бинарник. `O_CLOEXEC` из починки 4 остаётся второй линией обороны.
Проверено: замок держит ровно один дескриптор, копия работает устойчиво и пишет свой лог.

**Установщик больше не молчит.** Он пишет `update-install.log` рядом с данными: разобранная цель,
результат копирования, результат запуска. Разбирать «обновление не работает» по отчётам о падении и
опросу `ps`, как пришлось в этот раз, больше не нужно.

После всех починок проверено сквозняком на настоящей 1.0.7, собранной из истории: установщик,
унаследовавший замок, копирует бандл (1.0.7 → 1.0.8) и поднимает обновлённую копию; панель вторым
табом не открывается.
```
[19:03:02] цель: …/SignalBox.app, pid прежней копии: 99999
[19:03:03] скопировано
[19:03:03] обновлённая копия запущена
```

⚠️ **Порядком вложений управлять НЕЛЬЗЯ, и правило «виндовый архив первым» — неверное.**
Здесь оно стояло с 2026-08-11 и было выведено рассуждением, а не проверкой; на живом API
измерено обратное — GitHub сортирует вложения **по имени файла**. Подробности и решение
владельца — в §7, дублировать их тут незачем. Оставлено как след: это ровно урок §10.4.

**Логика вынесена в отдельный заголовок и покрыта тестом** `tools/test-update-asset.cpp`
(19 случаев, включает настоящий `UpdateAsset.h`, сети не трогает, идёт меньше секунды):
```
clang++ -std=c++17 -I src -o /tmp/t tools/test-update-asset.cpp && /tmp/t
```
🐞 **Тест сразу окупился:** наивный поиск подстроки «-mac» ловится внутри имени
`SignalBox-machine.zip`, и такой архив **крал выбор** у настоящей mac-сборки, стоящей следом.
Теперь после метки обязателен разделитель (точка, дефис, подчёркивание или конец имени). Живой
релиз этот случай не показал бы никогда — там один ассет.

**Скрипт упаковки — `tools/pack-mac.sh`** (`bash tools/pack-mac.sh` из корня, на выходе
`dist/SignalBox-<версия>-mac.zip`, версия читается из `kAppVersion`, чтобы имя и тег не разошлись):
- состав задан **списком разрешённого, а не исключений** — первый релиз проекта уехал с
  `cameras.txt` внутри (§7), и при обратной логике достаточно забыть один файл;
- внутри обязательна папка `SignalBox/` — установщик ищет `<распаковано>/SignalBox/SignalBox`;
- панель берётся из `build/Release/www` (источник правды), а не из копии в `build-mac/www`;
- адаптеры кладутся в `Contents/Frameworks/CrAdapter`;
- снимается карантин: **`/usr/bin/xattr -cr`** — именно по полному пути, см. грабку про
  питоновский `xattr` в PATH выше;
- в конце **самопроверка**: архив распаковывается тем же `ditto`, что и у установщика, и
  проверяется раскладка — нет `SignalBox/SignalBox` или затесались данные установки, скрипт падает.
- ℹ️ Файлы `._имя` внутри архива — норма: `com.apple.provenance` пользователю не снять, и `ditto`
  хранит его рядом с файлом. При распаковке `ditto` и Архиватором macOS они склеиваются обратно
  (проверено: в распакованном дереве их ноль). Карантин при этом снят, а мешает запуску только он.
- ⚠️ Чистка карантина при упаковке спасает только копию, отданную напрямую (по сети, на флешке).
  Скачанный с GitHub архив браузер пометит карантином заново, и распаковка перенесёт метку внутрь.

### Установщик .pkg с лицензией (2026-08-11)

`tools/pack-mac-pkg.sh` → `dist/SignalBox-<версия>-mac.pkg`. Ставит в `/Applications`, показывает
лицензию с кнопками «Принимаю»/«Не принимаю», в конце — экран с подсказками. Тексты правятся в
`res/license.txt` и `res/conclusion.txt`, окно установщика описано в `res/distribution.xml.in`.

⚖️ **`res/license.txt` — рабочий черновик, юристом НЕ смотренный** (написан 2026-08-11). Не общий
шаблон: разделы написаны под этот продукт — команды камерам и ответственность за отснятый
материал, зависимость от Wi-Fi и прошивок, компоненты Sony и MIT-библиотеки, поведение обновлений,
отсутствие отправки данных наружу. Два места оставлены пустыми намеренно, выдумывать их за
владельца нельзя: **юрисдикция** и **контакт**. Перед первой продажей текст обязан прочитать юрист
— вместе с условиями Sony на распространение их библиотек (§9).
⚠️ Длинные строки установщик по ширине окна сам не переносит — держать до ~80 символов
(сейчас максимум 78). Считать символы, а не байты: `awk 'length($0)'` на кириллице врёт вдвое.

🔴 **Чего .pkg НЕ делает — пароль не равен доверию.** Пароль или Touch ID, который спрашивает
установщик, — это разрешение писать в `/Applications`, и только. Доверие Gatekeeper определяется
подписью, а не способом установки: неподписанный `.pkg` сам блокируется ровно так же, как сейчас
блокируется `.app`.
✅ **Польза всё же есть, но другая:** файлы, которые кладёт установщик, карантином не метятся
(метку ставит браузер на скачанное, а `installd` payload не метит). То есть разрешить нужно **один
раз сам `.pkg`**, а установленная программа дальше запускается без вопросов. ⚠️ Проверено по
структуре пакета, но не на чистой машине — подтвердит только чужой Mac.

**`.pkg` — это ПЕРВАЯ установка, обновления по-прежнему ходят zip-архивом** (`pack-mac.sh`):
механизм обновления заменяет бандл на месте и про `.pkg` не знает. Выбор архива смотрит только на
`.zip`, поэтому `.pkg` в релизе ему не мешает (в тесте это случай «dmg + zip»).

Грабли, пойманные при сборке:
- 🔴 **`BundleIsRelocatable` обязательно выключать.** По умолчанию установщик считает приложение
  перемещаемым: если у пользователя уже лежит `SignalBox.app` где-то ещё (например, распакованный
  из zip в Загрузках), пакет обновит **ту** копию, а в `/Applications` не появится ничего — и при
  этом отрапортует «установка завершена». Лечится `pkgbuild --analyze` → `plutil -replace` →
  `--component-plist`.
- ⚠️ Проверять это надо по **содержимому** блока `<relocate>` в `PackageInfo`, а не по атрибуту
  `relocatable="false"`: он стоит и в пакете, собранном БЕЗ запрета. Выяснилось, когда собрал
  заведомо плохой пакет и проверил, что проверка на нём срабатывает, — первая версия проверки была
  холостой и не могла провалиться никогда.
- ⚠️ **В комментариях XML нельзя два дефиса подряд** — `productbuild` падает разбором. Поймал на
  собственном комментарии с названием ключа.
- ⚠️ `pkgutil --check-signature` на неподписанном пакете выходит с ненулевым кодом: при
  `set -e` + `pipefail` скрипт умирал молча ровно перед выводом причин. Тот же капкан уже ловил
  `ls` в `pack-mac.sh` — в обоих местах теперь `|| true`.

Подпись пакета — **отдельный сертификат** `Developer ID Installer` (у бандла — `Application`):
```
SIGNALBOX_PKG_IDENTITY="Developer ID Installer: ИМЯ (TEAMID)" bash tools/pack-mac-pkg.sh
```

### .app-бандл (2026-08-11)

✅ **Программа под macOS собирается настоящим `SignalBox.app`, а не голым бинарником.** Проверено
на живой машине: запуск через `open`, камера подключается, панель отдаётся, перезапуск и
выключение работают, значок в строке меню на месте.

**Зачем это было нужно** (по убыванию важности):
- 🔴 **Разрешение «Локальная сеть» теперь выдаётся SignalBox, а не Терминалу.** Замерено прямо:
  до выдачи разрешения автопоиск камеру не видел (`Автопоиск не увидел ZV-E1 — подключаюсь по
  сохранённому адресу`), после — `Обнаружена камера: ZV-E1`. У голого бинарника разрешение
  получал запускающий Терминал, и на чужой машине это был бы вечный источник «камеры не находятся».
- двойной клик раньше открывал Терминал, теперь запускает программу;
- подписать и нотаризовать можно только бандл;
- появилась иконка (`res/icon.icns`, собирается из `res/icon.ico` через `tools/make-icns.sh`).

**Раскладка** (её же ждёт установщик обновления):
```
SignalBox.app/Contents/
  MacOS/SignalBox            Info.plist
  Frameworks/*.dylib         Frameworks/CrAdapter/   ← адаптеры SDK
  Resources/www/             Resources/icon.icns
```
Адаптеры лежат внутри бандла не случайно: `libCr_Core` ищет их по
`[[NSBundle mainBundle] bundlePath]` + `Contents/Frameworks/CrAdapter` (проверено `nm`/`strings`
по самой библиотеке). У голого бинарника `bundlePath` — это папка с ним, поэтому сэмпл Sony и
клал `Contents/Frameworks` рядом с exe; в настоящем бандле путь сходится сам собой.

🔴 **Данные переехали в `~/Library/Application Support/SignalBox/`** (`plat::dataDir()`): туда
теперь пишутся `cameras.txt`, `cameras-known.txt`, `groups.json`, `settings.json` и **лог**.
Внутрь бандла писать нельзя — **любая запись ломает подпись приложения**, а без валидной подписи
нотаризация бессмысленна; вдобавок обновление заменяет бандл целиком и унесло бы данные студии.
Проверено: после полного цикла работы `codesign --verify --strict` проходит, внутри бандла не
появилось ни одного файла данных.
⚠️ **При переходе на бандл данные надо перенести руками** — программа старое место не ищет.
На этой машине перенесены `cameras.txt`, `cameras-known.txt`, `groups.json` (в нём была живая
группа GREEN).
**На Windows ничего не изменилось:** `dataDir()`/`resourceDir()`/`installRoot()` там все три
возвращают `exeDir()`, раскладка «данные рядом с exe» (§5) прежняя.

**Обновление теперь заменяет бандл целиком.** Внутри архива лежит `SignalBox.app` (на Windows —
папка `SignalBox`, `payloadName()` в `main.cpp`), цель — `plat::installRoot()`, а путь к бинарнику
внутри копии считается от собственных путей (`Contents/MacOS/SignalBox` против `SignalBox.exe`),
чтобы раскладка не жила в коде второй константой.

**Подпись.** CMake подписывает бандл в POST_BUILD **после** укладки содержимого — иначе
`codesign --verify` говорит «code has no resources but signature indicates they must be present»,
и это блокер для нотаризации. По умолчанию подпись ad-hoc; для релиза передать сертификат:
```
cmake -S . -B build-mac -DCMAKE_BUILD_TYPE=Release \
      -DSIGNALBOX_CODESIGN_IDENTITY="Developer ID Application: ИМЯ (TEAMID)"
```
💰 **Нотаризация всё ещё не сделана — нужен сертификат владельца** (99 $/год). Библиотеки Sony
идут от самой Sony только с ad-hoc подписью (проверено `codesign`), поэтому на чужом Mac
Gatekeeper будет ругаться на каждую. Порядок для релиза расписан в шапке `tools/pack-mac.sh`:
пересобрать с сертификатом → упаковать → `xcrun notarytool submit --wait` → `stapler staple` →
упаковать заново.
⚠️ **Наблюдение про ad-hoc:** распакованная в другое место копия просила разрешение «Локальная
сеть» заново (автопоиск снова не видел камеру, спасал сохранённый адрес). Похоже, без стабильной
подписи macOS считает копию по новому пути другим приложением. С Developer ID личность приложения
постоянна — ещё один довод за сертификат, помимо Gatekeeper.

⚠️ **Первый запуск сразу после пересборки тянется десятки секунд** (замерял 30 с и больше 90 с):
система заново проверяет свежесозданный бинарник и неподписанные dylib Sony. Дальше запуски
обычные — перезапуск с уже проверенным бинарником поднимает сервер за ~5 с. Не считать это
зависанием: процесс жив, просто молчит; смотреть `SignalBox.log`, а не «отвечает ли порт».
⚠️ И не читать лог сразу после старта: новый экземпляр переименовывает `SignalBox.log` в `.prev`
и заводит пустой, так что в первые секунды `grep` попадает ещё в **старый** файл и показывает
прошлый запуск. Обжигался на этом дважды — ждать появления строки `[tray]`.
⚠️ **Перед пересборкой SignalBox надо выключить** — ровно как на Windows: работающий бинарник
macOS перезаписать не даст (`ETXTBSY`).
⚠️ **Панель на Mac правится в `build/Release/www`, а НЕ в `build-mac/www`**: CMake копирует туда
первую поверх второй при каждой сборке (`CMakeLists.txt:151`), и правка в `build-mac/www` тихо
пропадёт — это тот же капкан «трёх копий» из §1, только в другой обёртке. Вся папка `build-mac/`
генерируемая и добавлена в `.gitignore`.

Что выяснено фактами:
- 🔴 **Gatekeeper блокирует dylib Sony**, они не подписаны и не нотаризованы (от Sony идут только
  с ad-hoc подписью — проверено `codesign`). До перехода на бандл приходилось прожимать **каждую**
  библиотеку вручную через Системные настройки → Конфиденциальность и безопасность.
  **Разобрано 2026-08-11, обе прежние записи здесь были неверны:**
  - 🐞 **`xattr -dr` карантин снимает прекрасно.** Прежний вывод «не помогло» — ложный: в PATH у
    владельца стоит **питоновский пакет `xattr`** (`~/Library/Python/3.9/bin/xattr`), который
    перекрывает системный и ключа `-r` не знает вовсе, так что команда просто падала. Работает
    **`/usr/bin/xattr -dr com.apple.quarantine <путь>`** — проверено на «скачанной» копии:
    38 файлов с карантином → 0, подпись бандла при этом цела.
  - ✅ **Прожимать каждую библиотеку больше не нужно.** Это была болезнь старой раскладки: голый
    бинарник и dylib рядом с ним — семь отдельных карантинных файлов, каждый оценивался
    Gatekeeper'ом сам по себе при загрузке. В `.app`-бандле все семь **запечатаны подписью бандла**
    (`codesign -dvvv` показывает их как `Nested=`, они же в `_CodeSignature/CodeResources`), и
    Gatekeeper оценивает бандл как одно целое — то есть одно «Всё равно разрешить» на приложение,
    как у любой скачанной программы.
    ⚠️ Окончательно это подтвердит только чужой Mac, где эти библиотеки ещё ни разу не разрешали:
    на машине владельца прежние разрешения уже выданы и чистого опыта не получить.
  - ⚠️ В macOS 15 Apple убрала обход «правый клик → Открыть» для неподписанных программ: путь
    теперь только через Системные настройки → Конфиденциальность и безопасность → «Открыть всё равно».
  💰 Нотаризация (99 $/год) убирает и это единственное нажатие. Второй, менее очевидный довод за
  сертификат — **стабильная личность приложения**: копия по новому пути просила разрешение
  «Локальная сеть» заново (§14, .app-бандл), а с Developer ID личность не меняется, и разрешение
  переживает обновления. Бесплатная учётная запись Apple Developer не подходит: она даёт только
  сертификаты `Apple Development` для локальной отладки, нотаризовать ими нельзя.
- 🔴 **`CrChar` зависит от `UNICODE`** (`CrTypes.h`): с ним `wchar_t`, без него `char`. Сэмпл Sony
  определяет `UNICODE` **только под Windows** (`RemoteCli/CMakeLists.txt:76`), значит на macOS SDK
  отдаёт обычный UTF-8 `char*`. У нас это разруливает перегрузка `plat::utf8From`, а `UNICODE` в
  CMake теперь под `if(WIN32)` — определить его на Mac значит разойтись с dylib по ABI.
- ✅ `libCr_Core.dylib` из пакета `CrSDK_v2.02.00_20260610a_Mac` — **universal (x86_64 + arm64)**,
  проверено `lipo` на M1. Порт нативный, Rosetta не нужен.
- 🔴 **Адаптеры на macOS ищутся в `Contents/Frameworks/CrAdapter`**, а не рядом с бинарником, как
  на Windows (так делает сэмпл Sony). CMake переносит их туда сам.
- ⚠️ macOS 14+ требует разрешение **Local Network**, иначе автопоиск (SSDP-мультикаст) молча
  ничего не находит. Для запуска из Terminal разрешение выдаётся Терминалу:
  Системные настройки → Конфиденциальность → Локальная сеть.
- Брандмауэр: `firewallSupported()` = false — понятия «правило на приложение заранее» в macOS нет,
  система спрашивает сама при первом входящем соединении.

**Правила слоя:** в `Platform.h` нет системных заголовков; все строки и пути — **UTF-8
`std::string`** (конверсия в `wchar_t` спрятана внутри реализации); функции не бросают исключений.
Заодно ушёл `std::ifstream(std::wstring)` — это расширение MSVC, которого нет нигде больше.

## 15. Камеры Blackmagic — разведка (2026-08-18)

Владелец хочет управлять из SignalBox не только Sony, но и **Blackmagic по локальной сети**.

### 15.1 Управление включается на каждой камере — и как это диагностировать

Официальное требование из мануала: REST-управление работает, **только если на камере включён
Web Media Manager** (Blackmagic Camera Setup → Network Access). Пока он выключен, камера
отвечает по HTTP, но API не отдаёт.

🔴 **Сигнатура выключенного управления — ложно «сломанный» API.** Любой путь, и настоящий, и
заведомо выдуманный, ведёт себя ОДИНАКОВО:
```
GET /control/api/v1/video/iso        → 307 Location: /control/api/v1/video/iso/   → 404
GET /control/api/v1/totally-bogus    → 307 …                                      → 404
```
Ни `401`, ни `403` — поэтому «нужна авторизация» здесь **неверный вывод**. Признак того, что
управление ВКЛ: `GET /control/api/v1/video/iso` отвечает `200` и JSON сразу, без слэша и редиректа.
Отличать «камеры нет» от «управление выключено» стоит и в панели: по mDNS камера видна всегда
(§15.6), так что SignalBox может честно сказать «найдена, но REST не включён», а не «офлайн».
На это ушло полразведки — 80 и 443 открыты, TLS-сертификат подлинный
(`CN=PYXIS-6K.local, O=Blackmagic Design`), а API молчит.

### 15.3 REST: что проверено вживую

База — `http://<камера>/control/api/v1`, обычный HTTP (не HTTPS), JSON. Чтение — `GET`,
изменение — `PUT`/`POST`, успех — **`204 No Content`** с пустым телом.

| `/video/iso` · `/video/gain` | `1250` · `10` дБ |

правило §10.0.1 «ничего не выдумывать» здесь встроено в API, зашитые таблицы не нужны:
- `/video/supportedISOs` — 25 значений, 100…25600; `/video/supportedGains` — −12…+36 дБ шагом 2;

  текущий режим измерения — `/video/shutter/measurement` (было `ShutterSpeed`);
- диапазоны: `/video/whiteBalance/description` → 2500…10000 K, `…Tint/description` → ±50;
- **`/lens/iris/description` → `{"apertureStop":{"min":4,"max":22},"controllable":true}`**;
- **`/lens/zoom/description` → `controllable:false`** (объектив 24–105 без мотора) — контрол зума

- `/lens/focus/autoFocus` → `{"supported":true,"enabled":true,"mode":"OneShot","state":"Idle"}`,

ND-фильтра нет, контрола в карточке быть не должно. У других моделей BM он есть, так что
наличие проверять по ответу, а не по модели.

**`GET /event/list` — перечень всех свойств камеры, 161 путь.** Удобная точка входа, чтобы

`system` 5, `livestreams` 4, `cloud` 3, `media` 3, `presets` 2, `timelines` 2, `access` 1.

✅ **Запись свойства проверена и обратима:** `PUT /video/whiteBalance {"whiteBalance":3200}` →
`204`, чтение назад → `3200`, возврат `5500` → камера снова `5500`. Тело `PUT` — той же формы,
что отдаёт `GET`.

### 15.4 🔴 Запись: `POST`, а не `PUT`, и `204` ≠ «применилось»

**Контракт из спеки самой камеры** (`TransportControl.yaml`):
- старт — **`POST /transports/0/record`**, тело необязательно (можно `{"clipName":"…"}`);
- стоп — **`POST /transports/0/stop`**;
- ⚠️ `PUT /transports/0/record {"recording":bool}` и `PUT /transports/0/stop` помечены
  **DEPRECATED**, «will be removed in a future version». Писать сразу на `POST`.
- чтение — `GET /transports/0/record` → `{"recording":bool}`.

🔴 **`204` означает «команда принята», а НЕ «действие произошло».** Замерено на живой камере:
`POST /transports/0/record` вернул `204`, а `recording` остался `false`, и события об изменении
не пришло вообще — потому что **в камере не было карты**. Камера промолчала об этом успехом.
Практический вывод тот же, что и у Sony (§10.0.2, §3 «камера применяет не то значение»):
**отправить мало, надо сверять по факту**. Кнопка REC в панели обязана загораться по
`recording:true`, пришедшему ОТ камеры, а не по факту отправки команды — принцип «кнопка сама
и есть индикатор» из §6 здесь работает как надо.

### 15.5 WebSocket — состояние приходит само

```
ws://<камера>/control/api/v1/event/websocket
```
Проверено живьём самодельным клиентом на голых сокетах (без библиотек — важно, что в C++ это
повторяется так же):
- рукопожатие → `101 Switching Protocols`, заголовки `Server: BlackmagicDesign`, `X-BMD-Schema: 1.0`;
- сразу после открытия камера сама шлёт `{"data":{"action":"websocketOpened"},"type":"event"}`;
- действия: **`subscribe`**, `unsubscribe`, `listSubscriptions`, `listProperties`. Запрос —
  `{"type":"request","id":1,"data":{"action":"subscribe","properties":["/transports/0/record",…]}}`;
- ✅ **ответ на `subscribe` содержит `success:true` И текущие значения** (`data.values`) — то есть
  подписка заодно заменяет первичный опрос, отдельный `GET` не нужен;
- изменения приходят как
  `{"data":{"action":"propertyValueChanged","property":"/video/whiteBalance","value":{…}},"type":"event"}`.
  Проверено: меняли WB через REST — push прилетал **раньше, чем завершался сам `PUT`**;
- подписаться можно на любое из свойств `/event/list`, в том числе по шаблону.

**Следствие для архитектуры: опрос ~1/сек, как у Sony, для BM не нужен вообще.** Это и дешевле,
и быстрее.
⚠️ **`/transports/0/timecode` — пожарный шланг: ~12–13 событий в секунду, постоянно, даже когда
камера ничего не пишет** (замерено: 68 событий за 5.4 с на простое). Подписываться на таймкод
выборочно (например, только для пишущей камеры) или прореживать, иначе панель захлебнётся.

### 15.6 Автопоиск камер — есть, IP руками вводить не придётся

Камеры анонсируют себя в **mDNS/Bonjour** под **`_http._tcp.local`**, и в TXT-записи уже лежит
всё нужное — до всякого обращения к API:
```
capabilities = cameraControl          ← камера сама заявляет, что ею можно управлять
product name = PYXIS 6K   product id = BEEC   release version = 10.2
device name  = PYXIS 6K 3             ← имя, которое видно в Camera Setup
unique id    = 86F9BEB995004B87A3FE4F900FD04D83   ← СТАБИЛЬНЫЙ ключ камеры
```
Найдены все три камеры разом, с именами и IP. ⚠️ **Фильтровать обязательно по
`capabilities=cameraControl`**: на `_http._tcp` в той же сети висят ATEM, сетевые свитчи, роутер
и десяток камер Hikvision — по одному лишь типу сервиса в список попадёт вся студия.
ℹ️ TXT показывает даже подключённое к камере устройство (`connected device` = телефон с
приложением Blackmagic Camera) — то есть занятость камеры видна со стороны.

**Ключ камеры — `unique id`, не IP** (§15.0). Смена адреса по DHCP не должна выглядеть как новая
камера. Это чище, чем возня с MAC у Sony (§4.3).
**Как делать:** mDNS — это мультикаст UDP на `224.0.0.251:5353`, той же природы, что SSDP,
который SignalBox уже шлёт для Sony, — то есть отдельная чужая библиотека не нужна, плуминг
знакомый. Ручной ввод IP оставить запасным путём, механизм `cameras.txt` уже есть (§4.2).

### 15.7 🔴 Картинка: в карточке BM её не будет — и это правильно

**Control-API кадров не отдаёт.** Ни JPEG-тайла, ни превью — ничего похожего на сониевский
`liveview` (§2, §6). `/media/*` — это доступ к УЖЕ ЗАПИСАННЫМ клипам на карте, а `/monitoring/*`
— настройки ФИЗИЧЕСКИХ выходов (LCD / MainSDI / FrontUSBC: яркость, LUT, zebra, focus assist),
а не сетевой видеопоток.

Картинку BM отдаёт **отдельным каналом**: встроенный движок **H.264/H.265 → SRT/RTMP**
(`/livestreams/0`, на камере `available:true`, формат `1920x1080p25`) плюс SDI/HDMI.
Именно так работает и приложение Blackmagic Camera на iPad, из-за которого возник вопрос
«а почему у них картинка есть»: управление у него по тому же REST, а видео — обычный кодированный
поток, который планшет декодирует **аппаратно**. Разница не в камере, а в клиенте: у нас клиент —
**браузер** (в том числе док OBS), а он сырой SRT/H.264 не проигрывает.

Чтобы показать PYXIS в нашей панели, SignalBox пришлось бы принять поток → декодировать →
перекодировать в то, что ест браузер (HLS/WebRTC/MJPEG) → раздать. Это подсистема класса ffmpeg
внутри процесса, кроссплатформенная, с большой внешней зависимостью — прямо против идеологии
«один лёгкий процесс без чужих больших библиотек».

🔴 **Решение владельца (2026-08-18): через OBS картинку НЕ отдаём — программа должна быть
самодостаточной.** Ассистент предлагал делегировать превью в OBS (студия и так в нём работает,
а он принимает SRT/RTMP нативно) — **предложение отклонено**: SignalBox не должен зависеть от
стороннего приложения в том, что показывает оператору. Превью камер Blackmagic **будет внутри
программы**; это отдельная задача, к которой возвращаемся после управления.

Практически это значит, что путь «принять поток → декодировать H.264/H.265 → отдать браузеру»
всё-таки придётся пройти, и его цена (см. выше) — реальная тема для отдельного проектирования:
где декодировать, во что перекодировать для браузера, сколько камер потянет один процесс.
**В первой версии BM-карточки превью нет** — но не потому, что от него отказались, а потому,
что оно вынесено в отдельный этап.

### 15.8 Чем BM-карточка отличается от сониевской

| | Sony | Blackmagic PYXIS |
|---|---|---|
| Живое превью | ✅ JPEG ~20 к/с из SDK | ❌ нет; поток в OBS (§15.7) |
| ND-фильтр | нет понятия | ❌ «not supported on this device» |
| Перегрев | ✅ `overheat`, оповещение (§3) | ❌ **свойства нет** среди 161 |
| Батарея/питание | ✅ | ✅ `/camera/power` (`AC`, мВ, батареи) |
| Таймкод | нет | ✅ живой, `/transports/0/timecode` |
| Tally | нет | ✅ `/camera/tallyStatus` |
| Цветокоррекция | нет | ✅ lift/gamma/gain/offset/contrast |
| Прокси и предзапись | нет | ✅ `proxyRecording`, `prerecord` |
| Обновление состояния | опрос ~1/сек | ✅ push по WebSocket |

Черновой состав карточки BM (только то, что камера реально отдаёт):
шапка «модель · питание · таймкод · REC · tally» → формат (кодек/разрешение/fps/dynamic range)
→ экспозиция (ISO · Gain · Shutter · Iris · AE) → ББ (Kelvin + Tint) → фокус (AF/MF) →
строка «источник картинки: SRT → открыть в OBS».

### 15.9 Что это значит для кода (решений ещё не принято, кода нет)

- ✅ **Бинарного SDK нет.** В отличие от `Cr_Core` (§14) — нечего линковать, нет чужих dylib,
  **нет боли с подписью, Gatekeeper и нотаризацией**. Чистый HTTP + JSON.
- **Нужен HTTP-клиент с `PUT`/`POST`:** в слое сейчас только `plat::httpGet` (§14, таблица) —
  он умеет один `GET` и заводился под проверку обновлений.
- **Нужен клиент WebSocket.** Проверено, что он пишется на голых сокетах: рукопожатие +
  разбор кадров + **обязательная маскировка кадров клиент→сервер**. Шим из `HttpServer.h`
  (`Socket`, `sendAll`, `recvSome`, `setRecvTimeout`, `setNoSigPipe`) переиспользуется, и
  API камеры — plain HTTP, так что TLS не нужен. В платформенный слой это тащить незачем.
- **Абстракция бэкенда:** вынести интерфейс из сониевской `CameraSession`, рядом положить
  реализацию BM. Форма `status.json` (§2) уже вендор-нейтральна — добавить поле вида `vendor`,
  панель по нему рисует свой тип карточки.
- **Ключ камеры — `unique id`**, IP только адрес.
- **Никакого опроса для BM** — подписка (§15.5), но не на таймкод оптом.
- ⚠️ **Сверять применение** — §15.4.

### 15.10 Не проверено

### 15.11 В копилку §10 (методология)

- **«API сломан» и «API выключен» выглядят одинаково.** Первое обращение к камере дало
  307→404 на всех путях, включая выдуманные, — и это был не баг и не авторизация, а
  невключённый Web Media Manager. Прежде чем чинить, проверить заведомо ложным путём: если
  ответ тот же, дело не в конкретном эндпойнте.
- **Спрашивать железо, а не память.** Точные адреса (`/transports/0/…`, а не `/transport/…`),
  устаревший `PUT` и отсутствие ND — всё это выяснилось только из спеки, которую отдаёт сама
  камера, и из живых ответов. Ни один из этих трёх фактов не был очевиден заранее.
- **Успешный код ответа — не доказательство результата** (§15.4). Ровно тот же урок, что с
  выдержкой у Sony (§3), только в другой обёртке.
- **Не додумывать причину чужого действия.** Две камеры «перестали отвечать» между шагами —
  выглядело как DHCP; на деле владелец сам выключил на них управление. Спросить дешевле, чем
  строить теорию.

## 16. Проект интеграции Blackmagic (2026-08-18) — решения приняты, кода нет

Продолжение §15: там факты с железа, здесь — как это встроить. **Ни строки кода ещё не
написано.** Раздел писался после чтения существующего кода, а не «вообще».

### 16.0 Что диктует нынешний код

| Факт | Следствие |
|---|---|
| `g_cams` — `vector<unique_ptr<CameraSession>>`, конкретный сониевский тип | нужен общий интерфейс, иначе второй вендор не встанет |
| `buildStatusJson()` зовёт `readStatus()` — **живой I/O к камере раз в секунду** | для BM так нельзя: состояние приходит подпиской, отдавать надо кэш |
| `resolveTargetsByIp()` — группы, клавиши и MIDI адресуют камеры **по IP** | у BM IP не ключ (DHCP), нужен стабильный идентификатор |
| `handleCmd()` — строковый switch по `action` | ложится один в один на «каждый бэкенд знает свои действия» |
| Панель: `cards[cam.id]`, членство в группе через `e.ip`, одна фабрика `buildCard()` | второй тип карточки + переход с `ip` на ключ |
| `runAction`/`toggleRecGroup` читают `cachedRecording()` | интерфейсу нужен дешёвый неблокирующий `recording()` |

### 16.1 Интерфейс `cam::ICamera`

Узкий, в отдельном заголовке; `SonyCamera` — тонкая обёртка над нынешним `CameraSession`
(его логику не трогаем), `BmdCamera` — новая реализация.
```cpp
virtual Vendor vendor() const; virtual std::string key() const;
virtual std::string idLabel() const; virtual int index() const;
virtual bool online() const; virtual bool recording() const;
virtual bool command(const std::string& action, const std::string& value);
virtual std::string statusJson() const;      // СВОЙ фрагмент
```
🔴 **`statusJson()` у каждого вендора свой** — не общий `CamStatus` со всеми полями обоих
марок. Именно это реализует решение владельца «карточки разные» (§15.8): у Sony фрагмент
ровно такой, как сегодня (ничего не ломается), у BM — свой, с таймкодом и tally, но без
`overheat` и `micGain`. Общая только шапка: `key, id, model, vendor, online, rec`.
Неизвестное действие в `command()` — `false` и строка в лог, а не падение (как в `runAction`).

### 16.2 ✅ Ключ камеры — и почему миграция `groups.json` НЕ нужна

- **Sony → ключ = IP** (в точности как сейчас);
- **BMD → ключ = `bmd:<unique id>`** (стабилен при смене адреса, §15.6).

`resolveTargetsByIp` становится `resolveTargetsByKey`, и **старые `groups.json` работают без
единой правки**: там лежат сониевские IP, они же и есть ключи. Ни миграции, ни переписывания
файла — в отличие от истории с `binds` (§3), где миграция была обязательна. Панель меняет
`e.ip` на `e.key` (одна замена), IP остаётся тем, чем и был: адресом для показа.

### 16.3 Потоки

- `BmdCamera` держит **свой поток WebSocket** и складывает состояние в кэш под мьютексом;
  `statusJson()` только читает кэш — **в потоке опроса ни одного сетевого вызова**. Sony
  работает как прежде.
- Обрыв WS → переподключение с паузой; пока лежит — камера офлайн.
- Команды идут прямым REST из HTTP-потока (на LAN это единицы миллисекунд).
- **Автопоиск живёт в существующем потоке `discoverer`** (те же ~5 с). Новых потоков не заводим.

### 16.4 Новые модули — в общем коде, НЕ в платформенном слое

| Модуль | Зачем |
|---|---|
| `src/net/Socket.h` | вынести сокет-шим из `HttpServer.h`, чтобы сервер и клиент делили один код |
| `src/net/HttpClient.h` | GET/PUT/POST с JSON. `plat::httpGet` умеет только GET и нужен для GitHub, где TLS; **API камеры — plain HTTP**, TLS не нужен |
| `src/net/WsClient.h` | WebSocket: рукопожатие, кадры, **маскировка клиент→сервер**. Проверено вживую, ~150 строк без библиотек |
| `src/net/MdnsBrowser.h` | автопоиск: мультикаст UDP `224.0.0.251:5353` — та же природа, что SSDP у Sony |
| `src/net/Json.h` | ⚠️ нынешние `jsonGet`/`jsonGetStringArray` — поиск подстроки; на вложенных объектах и массивах (`supportedShutters`, `lens/iris`) это источник тихих багов. Нужен маленький парсер (~200 строк, без зависимостей) |

Граница платформенного слоя (§14) при этом цела: сокеты BSD одинаковы везде, и это ровно тот
довод, по которому `HttpServer.h` в слой не попал.

### 16.5 Сверка применения — обязательна

Из §15.4: **`204` не значит «применилось»**. У `BmdCamera` тот же приём, что у сониевского
`reconcileLocked()`: запомнили, чего просили → ждём подтверждения (событие WS приходит быстрее,
чем ответ на сам запрос) → не сошлось, досылаем, не больше 3 раз → сдаёмся и пишем в лог
«больше не настаиваю». **Кнопка REC загорается только по `recording:true` от камеры**, а не по
факту отправки — принцип «кнопка сама и есть индикатор» (§6).

### 16.6 Панель

- `buildCard()` ветвится по `cam.vendor` на две фабрики; общий каркас (шапка, группа,
  перетаскивание) переиспользуется, метрики регуляторов остаются общими (§6).
- ✅ **Смешанные группы получаются бесплатно:** адресация по ключу, а групповая запись и так
  шлёт один запрос `{cams:[…]}`. Одна кнопка «Запись» в зале поднимет и Sony, и PYXIS —
  ровно то, ради чего всё затевается. Горячие клавиши и MIDI работают на BM сразу.
- У BM-карточки в первой версии Live Preview нет. 🔴 **Не потому, что картинку отдали OBS** —
  владелец его отклонил (§15.7): превью должно жить внутри SignalBox и делается отдельным этапом.

### 16.7 Решения владельца (2026-08-18)

- 📹 **Объём первой версии BM-карточки:** REC + таймкод + питание + tally + формат, **плюс

### 17.4 🔴 Gain и ISO у PYXIS — ОДИН регулятор в двух единицах

Замерено на живой камере: `gain 0 dB` → `ISO 400`; `gain +12 dB` → `ISO 1600`;
`ISO 1250` → `gain 10 dB`. То есть **`gain(dB) = 20·log10(ISO/400)`**, база сенсора —
ISO 400, +6 dB = вдвое больше ISO. Диапазоны совпадают: ISO 100…25600 ↔ −12…+36 dB.
⚠️ Держать в карточке оба — значит сбивать оператора с толку: он решит, что это разные настройки.
✅ **Решено 2026-08-20 конструктором карточки (§20):** оба лежат в списке доступных параметров,
а в карточку оператор кладёт те единицы, в которых сам думает. В подсказке к каждому прямо
написано «то же, что ISO/Gain, в других единицах». По умолчанию в карточке BM стоит ISO — как и было.

### 17.8 Скорость управления — что замерено и что сделано (2026-08-19)

Задача владельца: сделать управление максимально быстрым, не перегружая ПК и камеры и не
расшатывая программу. Двигались замерами, а не догадками.

**Где на самом деле терялось время.** Команда «туда» уже была мгновенной: `/cmd` отвечает за
**13–28 мс**, камера применяет за **24–39 мс**. Тормозила ОБРАТНАЯ связь — от 172 до 1033 мс,
потому что упиралась в два кванта по секунде: такт агрегации `/status.json` и опрос панелью.

**Сделано:**
1. **Событийная пересборка.** Камеры BM будят сборку статуса сами (`bmd::setOnChanged`) — у них
   и так есть подписка. У Sony событий нет, поэтому остался страховочный такт
   `kStatusIdleTick` = **100 мс**.
2. **Версия и 304.** `/status.json` отдаёт `X-Status-Seq`, принимает `?seq=N` и отвечает **304
   без тела**, если ничего не менялось — тот же приём, что у кадров live view (§6). Версия
   двигается ТОЛЬКО при реальном изменении тела.
3. **Панель опрашивает раз в 100 мс** вместо секунды и на 304 ничего не перерисовывает.

| | Было | Стало |
|---|---|---|
| Изменение НА камере BM → в `/status.json` | 172–1033 мс | **1–3 мс** |
| Sony: команда → видно в статусе | ~1000 мс | **110–160 мс** |
| Загрузка ядра, покой | 3.95% | **3.46%** |
| Загрузка под live view + статусом | — | **3.89%**, live view 25.2 к/с |
| Доля пустых ответов панели | — | **83% (304)**, трафик тел 3.8 КБ/с |
| Штатное выключение | ~1–4 с | **6.9 с**, «Готово.», сторож не сработал |

🔴 **Потолок Sony — не наш такт, а SDK.** При такте 50 мс задержка Sony составила 137 мс против
160 мс при 150 мс — то есть почти не изменилась: свойства отдаёт кэш SDK, и он обновляется
примерно раз в 110 мс. Гнаться ниже смысла нет, поэтому взяли 100 мс — там, где кривая уже легла.
✅ Побочно выяснилось: **`readStatus()` у Sony не ходит в камеру по сети** — весь цикл сборки
занимает <1 мс на обе камеры. То есть частый такт не грузит ни ПК, ни камеру Sony; в сеть уходит
только дочитывание таймкода у BM (1 запрос в секунду).

🔴 **SSE и long-poll отвергнуты по факту устройства сервера.** `HttpServer` строго
последовательный: `accept` → обработка → `close`, одно соединение за раз. Удержанное соединение
заблокировало бы и панель, и live view, и команды. Мгновенный push в браузер потребовал бы
сделать сервер многопоточным — это отдельная работа с риском для стабильности, а выигрыш поверх
нынешних ~50 мс средней задержки невелик.

⚠️ **Грабля методики:** замер частоты опроса ИЗ БРАУЗЕРА дал чушь (0% ответов 304 и всплески по
8 запросов за 8 мс). Причина — вкладка была скрыта, а браузер душит таймеры в фоне и потом
выпускает их пачкой. Это ровно предупреждение §6 про фоновые вкладки, только теперь оно
подтвердилось и на опросе статуса. Мерить такими вещами можно только скриптом со стороны или при
видимой вкладке.

## 18. Как устроен Live View у камер Sony (разбор + замеры 2026-08-19)

Раздел объяснительный: §6 описывает, как превью выглядит в панели, а здесь — что происходит под
капотом и во что это обходится. Написан по коду и подтверждён замерами на живой ILCE-7SM3.

🔴 **Это не видеопоток.** Никакого H.264 и никакого «стрима»: камера отдаёт **отдельные JPEG**,
один за другим, а браузер показывает их подряд. Отсюда все свойства механизма.

```
   КАМЕРА Sony              SignalBox (ПК)                    БРАУЗЕР
  ┌────────────┐   ┌────────────────────────────┐   ┌─────────────────────┐
  │ live view  │──▶│ liveViewWorker тянет кадры │──▶│ панель просит       │
  │  по Wi-Fi  │   │            ↓               │   │ /liveview/<n>.jpg   │
  │  (PTP-IP)  │   │ кэш: последний JPEG + seq  │◀──│ раз в 33 мс, с seq  │
  └────────────┘   └────────────────────────────┘   └─────────────────────┘
```

### 18.1 Звено «камера → ПК»

`liveViewWorker` (main.cpp) в цикле зовёт `CameraSession::grabLiveView`, а тот — `GetLiveViewImageInfo`
(размер следующего кадра) и `GetLiveViewImage` (сам JPEG). Оттуда же приходят рамки фокуса, лиц и
трекинга; камера отдаёт их **только при включённом `OSDImageMode`**, который код включает один раз
при первом кадре (§11).

🔴 **Кадры тянутся ТОЛЬКО у камер с открытым превью.** Признак активности — панель просила кадр за
последние **1.5 с** (`activeWindowMs`). Закрыли превью — через полторы секунды программа перестаёт
дёргать камеру совсем. Закрытое превью не стоит ничего ни ПК, ни камере.

### 18.2 🔴 Частоту кадров задаёт КАМЕРА, а не программа

Ограничителя в коде нет. Пауза `frameGap = 5 мс` в цикле нужна не для ограничения частоты, а чтобы
не крутить пустой цикл и уступать процессор. Искусственный потолок 7 к/с, который был раньше, снят.

Дальше работает **`seq`** (номер кадра):
- камера нередко отдаёт **один и тот же кадр несколько раз подряд**;
- программа сравнивает новый JPEG с предыдущим и увеличивает `seq` **только если картинка реально
  изменилась**, иначе клиент качал бы дубли;
- панель присылает номер уже показанного кадра, и на неизменившийся приходит **304 без тела**.

То есть панель спрашивает чаще, чем камера успевает отдавать, и лишние запросы стоят почти ничего.
**Реальная частота = сколько отдала камера**; она зависит от модели, Wi-Fi и загрузки тушки.

### 18.3 Звено «ПК → браузер»

`lvTick` в панели раз в **33 мс** запрашивает `/liveview/<n>.jpg?seq=N`. На 304 не делается ничего.
Полученный JPEG превращается в `blob`, подставляется в `<img>`, старый URL освобождается
(`revokeObjectURL` — без него течёт память). Рамки фокуса и лиц приходят заголовком `X-Cam-Frames`
и рисуются поверх картинки.

### 18.4 Замеры на живой ILCE-7SM3 (12 с наблюдения)

| Что | Значение |
|---|---|
| Запросов от панели | **25.5/с** (это её такт 33 мс) |
| Из них НОВЫХ кадров | **15.3/с** ← реальная частота камеры |
| Пустых ответов (304) | 121 из 306 |
| Размер кадра | **12–13 КБ** |
| Поток ПК → браузер | **1.6 Мбит/с** |
| Загрузка ядра: превью закрыто | 3.90% |
| Загрузка ядра: превью открыто | 4.39% |
| **Цена live view** | **≈0.5% ядра на камеру** |

Для сравнения, прежний замер на ZV-E1 (§6): ~20 к/с, кадр 12–42 КБ, 2–5 Мбит/с. Разброс между
моделями нормален — потолок задаёт камера.

### 18.5 Почему так дёшево для ПК и дорого для камеры

✅ **Программа не декодирует и не пережимает картинку**: JPEG как пришёл от камеры, так и уходит в
браузер байт в байт. Вся работа — переложить буфер, отсюда и 0.5% ядра.
⚠️ **Настоящая нагрузка — на самой камере**: тушка непрерывно кодирует JPEG и гонит их по Wi-Fi.
Это прямо связано с перегревом: у ZV-E1 состояние нагрева доходило до `2` после нескольких часов
трансляции превью (§3).
Практическая прикидка: превью на 4 камерах ≈ 2% ядра и ~6 Мбит/с — для ПК пустяк, но для Wi-Fi и
для самих камер уже заметно.

**Если понадобится СНИЗИТЬ частоту** (беречь камеры от нагрева, разгрузить эфир) — это одна строка:
увеличить `frameGap` в `liveViewWorker` либо такт `setTimeout(loop, 33)` в панели. Повышать нечего:
частота и так упирается в камеру.

### 18.6 Чем это принципиально отличается от Blackmagic

У Sony **SDK сам отдаёт готовые JPEG**, поэтому превью почти бесплатно по процессору. У PYXIS
такого канала нет вовсе: картинка идёт **настоящим H.264/H.265-потоком** (SRT/RTMP) или по SDI, и
её придётся принимать и декодировать — вот это уже будет стоить процессора всерьёз (§15.7).
Владелец решил, что превью BM должно жить внутри программы, а не отдаваться OBS, поэтому при
проектировании этого этапа сравнивать его с сониевским «почти даром» нельзя.

⚠️ **Мерить частоту только при видимой вкладке.** Браузер душит таймеры в фоне и потом выпускает их
пачкой; в свёрнутом доке частота падает. Это поведение браузера, а не программы (§6, §17.8).

## 19. Доводка по итогам живой работы в студии (2026-08-19)

Всё ниже найдено не в теории, а когда владелец работал панелью с тремя PYXIS и камерой Sony.
Каждый пункт — отдельный коммит, каждый проверен на живом железе.

### 19.1 Таймкод: подписка вместо опроса, и время записи рядом

Раньше таймкод дочитывался REST-запросом раз в секунду, и на подписку он не брался, чтобы «не
сыпал». Замер показал, что опасение было не там: подписка отдаёт **12.5 событий/с по УЖЕ
ОТКРЫТОМУ соединению и стоит 1.85 КБ/с**, тогда как частый REST означал бы новое TCP-соединение
на каждый запрос. То есть **подписка для камеры дешевле, а не дороже**.

🔴 **Порог обновления КВАНТУЕТСЯ.** Проверка порога происходит только в момент прихода события, а
события идут каждые ~80 мс, поэтому реальный период = `ceil(порог / 80 мс) × 80 мс`. Замерено:

| Порог | Период | Обновлений/с | Пустых ответов | Трафик тел |
|---|---|---|---|---|
| 50 мс | 80 мс | 12.5 | 0% | 32.8 КБ/с |
| 100 мс | 160 мс | 6.2 | 34% | 21.6 КБ/с |
| **200 мс** ← выбрано | 240 мс | 4.3 | 56% | 14.5 КБ/с |

Меньше 80 мс ставить бессмысленно — чаще камера не присылает. Выбрано 200 мс: кадры в панели
скрыты, видимая цифра меняется раз в секунду, и порог влияет лишь на то, как быстро
перещёлкивается секунда. Константа — `kTimecodeUiInterval`, таблица продублирована в комментарии
к ней, чтобы значение не подбирали вслепую.

⚠️ **Сверку пришлось развести с событиями** (`kReconcileInterval` = 400 мс): при 12 событиях в
секунду три попытки досылки сгорели бы за четверть секунды, и программа сдалась бы раньше, чем
камера успела применить значение.

**Время записи — отдельная величина.** Камера отдаёт `display` (часы камеры) и `timeline`
(длительность записи); в карточке был только первый. Теперь есть оба: вне записи показывается
таймкод, во время записи — длительность, красным. ⚠️ `recTime` вживую не проверен: без карты
`timeline` стоит на нуле.

**Показ — `ЧЧ:ММ:СС`.** Последняя группа таймкода это **номер кадра** (0..24 при 25p), а не
миллисекунды; оператору она не нужна. Режем в панели (`tcShort`), в `/status.json` остаётся
полное значение камеры. Разделителем перед кадрами бывает и `;` (drop-frame) — режем по обоим.

### 19.2 🔴 Три причины, почему на второй камере не работали ISO / выдержка / gain

Владелец подключил вторую PYXIS, и её органы управления оказались пустыми. Причин нашлось три,
все разные, и первая — самая коварная.

1. **Списки допустимых значений не читались вовсе.** Они берутся только в полном REST-опросе, а
   он делается не на каждом проходе. Если камера появилась на «неполном» такте, программа уходила
   в подписку с пустыми списками и REST больше не звала никогда. Панель гасит селектор без
   вариантов — выглядело как «параметры недоступны». Первая камера не страдала только потому, что
   была включена при старте и попала на самый первый проход, где опрос всегда полный. Классическая
   гонка, видимая лишь на второй камере. Теперь списки читаются гарантированно перед подпиской,
   а чтение вынесено в `readSupportedLists()`.
2. **Выдержка в режиме УГЛА не читалась и не писалась.** Эта камера стояла в `ShutterAngle`
   (180° = 18000), а код знал только `shutterSpeed`. Теперь режим определяется тем, какое поле
   прислала камера (самоисправляется при переключении на тушке), храним оба списка
   (`shutterSpeeds` и `shutterAngles`), отдаём соответствующий режиму и пишем в то же поле.
3. **Сверка не знала про `shutterAngle`** — сопоставляла только `shutterSpeed`, поэтому считала
   значение неизвестным, трижды зря досылала команду и писала «больше не настаиваю», хотя камера
   значение приняла.

Заодно: **смена формата помечает списки устаревшими** и они перечитываются на ходу — набор
допустимых выдержек зависит от частоты кадров, а опроса по кругу больше нет.

### 19.3 🔴 Молчание подписки НЕ значит, что камера жива

Владелец отключил две камеры, а в панели это никак не отразилось — просто **остановились
таймкоды**. Причина: пока подписка формально жива, камера не перепроверялась. Когда камеру
выключают, **сокет нередко остаётся открытым и просто молчит**: `recvText` уходит в таймаут,
`connected()` по-прежнему `true`, чтение таймкода проваливается молча, и камера навсегда остаётся
online со старыми значениями.

Теперь дочитывание таймкода служит заодно **проверкой живости**: три неудачи подряд (таймаут
запроса снижен до 1.5 с) — камера помечается офлайн, подписка гасится, кэш очищается.

**Проверено на живом железе, не трогая студийные камеры:** поднимался локальный TCP-прокси к
камере, который можно оборвать. Оба случая: обычный обрыв (сокет закрылся) — замечено сразу;
и главный — прокси держит сокеты открытыми и молчит, имитируя выключенную камеру: замечено за
**~5 с**.

**В панели у камеры BM теперь три различимых состояния:** рабочая; найдена, но REST-управление не
включено (жёлтая подсказка); и **не отвечает** — красная рамка, бейдж `Offline`, таймкод
`--:--:--`. Различать важно: первое чинится галочкой в Camera Setup, второе — питанием и кабелем.

### 19.4 Автоудаление пропавших камер — и почему сначала пришлось менять владение

🔴 В `main.cpp` прямым текстом стояло, что список камер **только растёт**: `resolveTargets`,
сборка статуса и поток live view копируют ссылки под мьютексом, а работают с ними **уже без
него**. Пока список не сокращался, сырой указатель жил вечно и это было безопасно. С удалением
так нельзя — объект мог бы исчезнуть у другого потока под рукой.

**Камеры переведены на `shared_ptr`**: камера доживает до последнего держателя, глобальная
блокировка не нужна. ⚠️ Заодно **номера камер стали монотонными** (`g_nextCamIndex`): раньше
индекс считался от размера списка, и номер выбывшей камеры достался бы новой — панель хранит
карточки по «CAM N», и карточка одной марки обновилась бы данными другой.

**Правило удаления:** камера BM убирается, если её не видно **ни в анонсах mDNS, ни на связи
дольше 5 минут** (`kForgetLostMs`). Перезагрузку камеры и короткий обрыв это переживает, переезд
в другую студию — нет. Камера с выключенным Web Media Manager **не удаляется**: она отвечает по
HTTP, значит физически на месте. Камеры Sony не трогаем — они и так исчезают из панели офлайн, а
их сессия держит хэндл SDK, который отпускать надо иначе.
⚠️ Потоки удалённых камер останавливаются **уже без мьютекса**: `join` под общей блокировкой
подвесил бы и статус, и команды.
Проверено подопытной камерой через прокси при временно сниженном пороге: исчезла через 25 с.

### 19.5 Угол затвора у Sony: камера его не отдаёт

Владелец попросил поддержать угловой режим и для Sony. **Полный дамп свойств живой ILCE-7SM3
(324 штуки)** показал, что чинить нечего: из затворных она отдаёт только `ShutterSpeed`, а
**`ShutterAngle`, `ShutterMode`, `ShutterModeStatus`, `ShutterSetting`, `ShutterSpeedValue`
отсутствуют полностью**; `ShutterModeSetting` и `ShutterType` приходят пустыми и только на чтение.
То есть A7S III через Camera Remote SDK угол затвора не сообщает — это ограничение камеры, а не
программы. Вычислять градусы из скорости и частоты кадров нельзя: это ровно то «выдумывание»,
которое запрещает §10.0.1, и камера всё равно не сказала бы, в чём хочет видеть выдержку оператор.

Поддержка добавлена на будущее, потому что свойство есть в SDK и его отдают кинокамеры Sony.
По доке SDK: `CrDeviceProperty_ShutterAngle`, тип `UInt32Array`, **значение = градусы × 1000**
(180000 = 180°), ноль = `CrShutterAngle_Disable`. Если камера отдала угол — он главнее скорости,
метки собираются целочисленно (`180°`, точка литеральная — §3), запись уходит в то же свойство,
панель подписывает контрол «Shutter °».
⚠️ **Вживую не проверено — не на чем.** Код защищён: камеры без этого свойства работают ровно как
раньше (проверено: 34 варианта выдержки, метки `1/4…`, запись проходит). Проверить, когда под
рукой окажется FX30/FX3 или другая кинокамера.

### 19.6 В копилку §10 (методология)

- **Гонка, которую видно только на втором экземпляре.** Списки значений читались лишь на первом
  проходе, и камера, включённая при старте, скрывала ошибку. Правило: проверять не только «первую
  камеру при запуске», но и «вторую, появившуюся позже».
- **Отсутствие ответа — тоже ответ, но его надо спросить.** Молчащая подписка выглядела как
  работающая. Живость надо проверять активно, а не выводить из того, что сокет не закрылся.
- **Прокси как способ ломать связь, не трогая железо студии.** Локальный TCP-прокси к камере
  позволил проверить и обычный обрыв, и «молчащий сокет», не выключая рабочих камер. Приём
  пригодится и дальше.
- **Дамп всех свойств вместо угадывания.** Вопрос «поддерживает ли камера угол затвора» закрылся
  за один запуск: 324 свойства, среди них нужного нет. Спорить с этим бессмысленно, а выводить
  ответ из документации SDK было бы ошибкой — там свойство есть, а у камеры его нет.

## 20. Конструктор карточки — что показывать, решает оператор (2026-08-20)

Задача владельца: удалённо крутится куда больше, чем влезает в карточку, а карточек на экране
должно помещаться много. Значит, набор параметров нельзя выбрать за оператора раз и навсегда —
пусть выбирает сам.

### 20.0 Решения владельца

- **Настраивается только середина карточки** — зона между строкой «Группа» и Live Preview.
  Шапка (модель, батарея, карта, таймкод, tally, REC), сама строка «Группа» и Live Preview
  постоянны: 🔴 **это индикаторы, а не параметры**, и настройке не подлежат.
- **Сетка по три параметра в ряд, строк сколько нужно.** Седьмой параметр сам заводит третью
  строку, десятый — четвёртую.
- **Настройка относится ко ВСЕМ карточкам марки**, а не к отдельной камере. Поэтому образец в
  настройках — **абстрактный**: подключена сейчас хоть одна камера этой марки или ни одной, на
  конструктор это не влияет вовсе.
- **Раскладка общая на студию** — хранится на сервере (см. 20.3), а не в браузере.
- **Sony и Blackmagic настраиваются по отдельности**: наборы параметров у них разные, общего
  списка быть не может (продолжение решения из §15.8 «карточки у марок разные»).

### 20.1 Как это устроено в панели

Карточка больше **не свёрстана жёстко**. Появился реестр параметров `PARAM_DEFS` — по списку на
марку; одна запись описывает параметр целиком:

| поле | зачем |
|---|---|
| `id` | как параметр лежит в сохранённой раскладке — **менять нельзя**, сломает чужие раскладки |
| `lab` | подпись в карточке |
| `hint` | пояснение в списке доступных параметров |
| `build(e)` | создаёт блок, вешает обработчики, ссылки складывает в `e.r[id]` |
| `update(e, d)` | заполняет блок из ответа камеры |

Сборка: `buildParams(e, vendor, host)` кладёт в сетку то, что перечислено в раскладке,
`updateParams(e, d)` обновляет ровно эти блоки. `updateSonyCard`/`updateBmdCard` остались только
на постоянную часть — перегрев, батарея, карта, таймкод, tally, формат.

🔴 **Ссылки на органы управления живут в `e.r[id]`, а не прямо в `e`.** Раньше было
`e.isoSel`, `e.shSel`, `e.micBox` и так далее; при настраиваемом составе такая ссылка пережила бы
свой элемент — оператор убрал параметр, а код по старой памяти лезет в удалённый узел. Теперь
ссылки создаются и умирают вместе с блоком.
✅ Побочно ушла давняя хрупкость: подпись выдержки бралась по индексу
(`querySelectorAll('.controls .ctl')[1]`), что при любой перестановке указывало бы не туда.

**Смена раскладки** = `applyLayout(vendor)`: сохранить на сервере и пересобрать зону параметров у
живых карточек этой марки. Пересобирается **только середина** — шапка, группа и Live Preview
остаются на месте, вместе с открытым превью и его потоком кадров.

**Неизвестный `id` молча выбрасывается** при загрузке: файл мог быть написан версией, где
параметр назывался иначе или его ещё не было. Ломаться из-за этого панель не должна.

### 20.2 Новые параметры (сервер их отдавал, а карточка не показывала)

| Марка | Параметр | Откуда | Примечание |
|---|---|---|---|
| Sony | **ББ (пресет)** | `wb{cur,opts,rw}`, команда `wb` | «Авто / Дневной свет / Облачно / …»; поддерживалось с самого начала, места в карточке не было |
| BM | **Iris** | `iris`, `irisControllable` | только показ (§17.7): списка шагов камера не даёт, а свою таблицу выдумывать нельзя |
| BM | **Auto Exp** | `autoExposure` | только показ; пока значением рулит автоэкспозиция, камера отвечает **403** на запись (§17.3) — оператору полезно видеть, почему |

По умолчанию раскладка — **ровно та, что была в карточке до конструктора**, поэтому у того, кто
ничего не настраивал, вид не изменился:
`sony: iso, shutter, aperture, micgain, wbk` · `bmd: iso, shutter, gain, wb, tint`.

### 20.3 Хранение: `cardlayout.json` на сервере

Схемой владеет **панель**, сервер только хранит — тот же уклад, что с `groups.json` (§3, §5):

- `GET /cardlayout.json` → содержимое файла; **файла нет → `{}`**. Набор по умолчанию знает
  панель, и дублировать его в C++ значило бы завести второй источник правды;
- `POST /cardlayout/save` → проверка «похоже на JSON-объект вменяемого размера» (≤64 КБ) и запись.
  Перечитывать нечего: сервер раскладку не использует;
- файл лежит в `plat::dataDir()` — рядом с exe на Windows, в `~/Library/Application Support/SignalBox/`
  на macOS (§5).

🔴 **Почему на сервере, а не в `localStorage`.** Свёрнутые группы нарочно живут в браузере: там у
каждого оператора свой зал (§6). Здесь наоборот — раскладка одна на марку и одна на студию:
настроили на ноутбуке, то же самое видит док OBS и телефон. Первая версия была сделана на
`localStorage` и по решению владельца переведена на сервер в тот же день.

Сохранение **с задержкой 300 мс**, как у групп: перетаскивание — это несколько правок подряд.
Пока ответ сервера не пришёл или сервера нет (панель открыта файлом, связь оборвалась), работает
набор по умолчанию: карточки должны появиться сразу, а не ждать настройку. ⚠️ Молчать о неудачном
сохранении нельзя — иначе человек решит, что настроил, а после перезапуска увидит прежнее;
поэтому на ошибку всплывает «Не удалось сохранить вид карточки».

🐞 **Заводя новый файл данных, добавить его в оба скрипта упаковки** (§7): данные установки в
архив попадать не должны, и `tools/pack-*` это проверяют.

### 20.4 Сам конструктор (Настройки → Камеры)

Разворачивающиеся строки **Sony** и **Blackmagic**. Слева образец карточки, справа — параметры,
которых в ней сейчас нет.

- 🔴 **Образец рисуется ТЕМ ЖЕ кодом, что и боевая карточка** (`sonyCardEl`/`bmdCardEl` +
  `buildParams`), поэтому показывает ровно то, что получится. Отдельно нарисованная картинка
  рано или поздно разошлась бы с делом — тот же довод, по которому настройки в §6 были
  **перенесены**, а не скопированы.
- Значения в образце — образцовые. Правило §10.0.1 «ничего не выдумывать» они не нарушают:
  здесь они ничем не управляют и за показания камеры себя не выдают, а в боевой карточке каждое
  значение приходит от самой камеры.
- Постоянная часть в образце приглушена и не нажимается — видно, что настраивается только середина.
- Перетаскивание: внутри карточки блок едет живьём и сетка перестраивается на ходу; из списка —
  место вставки показывается полоской, вставка по отпусканию. Бросок из карточки в список —
  убрать. Отпустили мимо (Esc, вне окна) — раскладка возвращается как была.
- ⚠️ **На телефоне перетаскивания нет**: HTML5 drag-and-drop не работает на тач. Поэтому у
  каждого блока «✕», а у каждого доступного параметра «+» — тот же запасной путь, что у выбора
  группы в карточке (§6).

### 20.5 🐞 Найден и починен баг, убивавший опрос целиком

Не связан с конструктором — вылез при проверке, **воспроизведён на версии из git**, чтобы не
приписать его себе.

**Симптом:** камера Blackmagic пропадает из `status.json` (ровно то, ради чего делался §19.4) —
и панель застывает со старыми карточками и меткой «нет связи». Выглядит как обрыв связи с
программой.

**Причина:** `sync()` при удалении карточки зовёт `lvStop`/`lvFsExit`, а те лезут в `e.lvFrame`.
🔴 **Живого превью есть не у всех марок** — у карточки BM узлов `lv-*` нет вовсе. Исключение
роняло разбор ответа целиком, `poll()` уходил в `catch`, и там `sync([])` падал снова.

**Лечение:** обе функции проверяют, что превью вообще есть. Проверено: карточка пропавшей камеры
теперь уходит, опрос живёт (`live: true`).

**В копилку §10:** *ошибка в общей функции проявляется только на той марке, у которой чего-то
нет.* Проверять удаление и очистку не только на Sony (там есть всё), но и на карточке, где
половины узлов не существует.

### 20.6 Метрики: ряды снова разъехались — и это было предсказуемо

Пока ряды жили в двух разных контейнерах (`.controls` и `.controls2`), разница высот была не
видна. В общей сетке она вылезла сразу: **27.5px** у ряда со списком против **24px** у ряда
«− значение +» (замерено, не на глаз). Лечение там же, где остальные метрики (§6): у `.ctl-row`
своя `min-height:28px`, содержимое по центру. Итог — **41.34px у всех блоков обеих марок**.

⚠️ Вторая такая же ловушка была в самом конструкторе: подсветка блока рамкой с полями делала ряд
образца **49.34px** против 41.34px в карточке, то есть настройка показывала бы не то, что
получится. Заменено на `outline` — он не занимает места в раскладке.

Проверялось макетом с подставными камерами (без обращения к студийному железу) и затем на живой

### 20.8 Что осталось по этой теме

- ✅ **Перезапущено, эндпойнты работают:** на живом сервере `GET /cardlayout.json` отвечает `200`

  задумано (набор по умолчанию знает панель).

- Возможное развитие, если попросят: блок на две ячейки (сейчас все одинаковой ширины в треть

## 21. Раскладка панели: ориентация, ширина групп, порядок карточек (2026-08-26)

Задача владельца: на компьютере удобнее, когда карточки в группе стоят **в ряд**, а не колонкой.
Из этого выросла цепочка правок по всей раскладке — вплоть до шапки группы. **Только панель,
C++ не менялся** (перезапуск программы всё же нужен: панель лежит внутри бандла — см. 21.7).

### 21.0 Решения владельца

- Переключатель ориентации — **три состояния по кругу**: Авто → Верт → Гориз. «Авто» по
  умолчанию и пересчитывается на лету; ручной выбор автоопределение выключает навсегда.
- Ширина карточки в горизонтали — **прежняя** (340…392 px), карточки переносятся на следующую
  строку. Растягивать их на всю ширину группы не стали: внутренности рассчитаны на эту ширину.
- Группы в горизонтали — **по левому краю**, а не по центру: карточки разных залов встают в
  общие колонки сверху вниз, глазу легче, и зона для перетаскивания всегда на одном месте.
- Выбор ориентации **помнится для каждого устройства**, а не для студии.

### 21.1 Ориентация: одна вёрстка, развёрнутая на 90°

Вертикальный и горизонтальный режимы — это **одна и та же вёрстка**, а не две:

| | группы | карточки внутри |
|---|---|---|
| **Верт** (как было) | плиткой, колонками по 392 px | колонкой, одна под другой |
| **Гориз** (`body.lay-h`) | каждая во всю строку, друг под другом | в ряд, с переносом |

Иначе никак: колонка группы шириной 392 px — это ровно одна карточка, ряд в неё не поместится.
Переключатель поэтому разворачивает **обе** сетки разом.

Хранение — `localStorage['signalbox.cardOrient']`, рядом со свёрнутыми группами.
🔴 **Не на сервере, в отличие от `cardlayout.json`.** Состав карточки — решение студии и общее
для всех (§20), а ориентация — свойство экрана, за которым сидит человек. Один сервер отдаёт
панель и на телефон, и на ПК, и в док OBS: общее на студию значение перетягивало бы одно
устройство под другое.

Автоопределение — `matchMedia('(min-width: 900px) and (orientation: landscape)')`.
900 px — это две карточки (392+392) с зазорами и полями; второе условие отсекает **вертикальный
монитор** (1080×1920 по ширине проходит, но по форме это колонка). Телефон в портрете и узкий
док в OBS отсекаются первым условием.

🔴 **Условие держим на `matchMedia`, а НЕ на замере `innerWidth` по событию `resize`.** Первая
версия так и была написана — и на проверке вьюпорт менялся, а `resize` не приходил: раскладка
оставалась прежней. `change` у медиазапроса приходит на любое изменение вьюпорта, включая
поворот телефона. Совпадает с CSS благодаря `<meta name="viewport" content="width=device-width">`.

### 21.2 Ширина группы — по числу карточек, но не больше, чем влезает

Группа шире, чем нужно её камерам, не растёт: пусто или одна камера — коробка с карточку, две —
на две, и так далее.

Первая версия считала ширину прямо в CSS: `min(100%, камер × 392px + зазоры + рамка)`. **Это был
баг, и владелец его поймал.** Для четырёх камер формула даёт 1623 px, на экране 1440 доступно
1412 — `min` упирал ширину в 1412, коробка оставалась во всю ширину, а внутрь влезало только три
колонки. Справа зияла пустая полоса ~190 px.

Дырка в самой постановке: считать надо не по числу **камер**, а по числу **колонок, которые
влезли**, — то есть делить доступную ширину на ширину карточки. CSS так не умеет (`floor()` ещё
не везде), поэтому расчёт живёт в JS — `sizeGroups()`:

```
колонок = min(камер, сколько влезает в ряд)
ширина  = колонок × --card-w + зазоры + поля с рамкой
```

- Поля и рамку функция **меряет с самого элемента**, а не берёт числом: у «Без группы» их нет, и
  одна формула покрывает обоих.
- Меряет от **родителя**, а не от самой группы: её ширину мы же и назначаем, и читать её обратно
  значило бы гоняться за собственным хвостом.
- CSS только применяет готовое `--grp-w`, с запасным `100%` — если скрипт не отработает,
  раскладка вернётся к прежнему поведению во всю ширину, а не развалится.
- 392 / 340 / 11 переехали в переменные `--card-w`, `--card-min`, `--card-gap`: эти числа теперь
  считают в двух местах (колонки внутри группы и ширина самой группы), разъехаться им нельзя.

Пересчёт зовётся из `placeCards()` (состав изменился) и из **`ResizeObserver`** на ряде групп
(ширина окна изменилась). Сравнение с прошлой шириной обязательно: `sizeGroups` меняет высоту
ряда, наблюдатель просыпается снова, и без отсечки он ходил бы по кругу.

Побочно это чинит и центровку подсказки «Перетащи сюда карточку камеры»: колонок теперь ровно
столько, сколько задано шириной, дорожки `auto-fill` заполняют тело без остатка, и подсказка
(`grid-column: 1 / -1`) встаёт по центру коробки, а не по центру недобранных дорожек.

### 21.3 Порядок карточек внутри группы

Порядок задаёт оператор перетаскиванием. Хранится **там же, где состав**: в самом массиве
`cams` — он и так упорядочен, схему менять не пришлось. У «Без группы» массива не было, поэтому
рядом с `groups` в том же файле лежит `ungrouped: [ключи]`.

🔴 **Проверено на живом сервере, что C++ стерпит лишний ключ:** `groups.json` он не трактует, а
пишет присланный объект целиком (§2, main.cpp `/groups/save`). Пробный объект с `ungrouped`
вернулся дословно, привязки перечитались, горячая клавиша зарегистрировалась. Файл студии после
опыта возвращён из бэкапа и сверен — совпадает.

- Точка вставки считается по-разному: вертикально решает только Y (колонка), горизонтально —
  сначала строка по Y, потом половина карточки по X (сетка с переносом).
- Вставка задаётся **ключом камеры, перед которой встаём**, а не индексом в DOM: `cams` может
  содержать ключи камер, которых сейчас нет в сети, и индексы разъехались бы.
- 🔴 **Ключи офлайн-камер из списков не вычищаются** — камера вернётся и встанет на своё место.
- Метка «встанет сюда» — полоса в зазоре, лежит `position:absolute`, поэтому не становится
  элементом сетки и не двигает соседей.
- Заодно починен `dragleave`: он гасил подсветку зоны и когда указатель просто переходил на
  карточку **внутри** неё — метка мигала бы на каждом движении.

### 21.4 🔴 Почему панель моргала на каждое перетаскивание

Две причины, обе устранены.

1. **`moveCam` звал `renderGroups()`**, а тот начинается с `groupsWrap.innerHTML = ''` и
   пересобирает все залы. Для перетаскивания это лишнее: набор залов не менялся, менялся состав,
   а его целиком раскладывает `placeCards` — он же обновляет счётчики, индикатор REC, подсказку
   пустой группы и селектор в карточке. Убирал же `renderGroups` не только рамки: вместе с ними
   из документа выдёргивались **все карточки разом**.
2. **Анимация появления висела на `.card`.** Карточка на миг покидает документ — вернувшись, она
   для браузера новая, и `animation: in` играет с нуля. Достаточно любой пересборки, чтобы вся
   панель заново проявилась.

Теперь появление играется **один раз**: анимация переехала на класс `.card.fresh`, который
вешается при постройке и снимается по `animationend`. Даже полная пересборка (добавление или
удаление зала) карточки больше не перепроявляет.

⚠️ **Общее правило, которое стоит держать в голове:** `renderGroups()` — операция «набор залов
изменился». Всё, что меняет только состав или порядок, обязано обходиться `placeCards()`.

### 21.5 Шапка группы

- **Поле имени больше не тянется на всю ширину.** `input` себя по содержимому мерить не умеет, а
  `flex:1 1 120px` отдавал ему всё свободное место. Ширину считает `fitName()`: меряет текст на
  канве тем же шрифтом, каким его рисует браузер. Атрибут `size` не годится — он считает по
  «средней букве», а у узкой Saira Condensed с `letter-spacing:.08em` промах такой, что поле
  оказывается уже текста. Пересчёт на каждое нажатие и один раз по `document.fonts.ready`:
  первый расчёт приходится на загрузку, когда свои шрифты ещё не приехали.
- **Регистр не навязывается** — убран `text-transform:uppercase`: имя показывается как набрали.
- **Имя по умолчанию — «Группа N»**, было «Зал N». Заменено во всех четырёх местах: новая
  группа, подстраховка при чтении файла, подстраховка при очистке поля, образец в конструкторе.
  Уже сохранённые названия не меняются.
- **Запись на зал — одна кнопка-индикатор** вместо пары «Запись»/«Стоп» с отдельным индикатором.
  Это тот же `.rec-btn`, что в карточке камеры: зелёная в покое, красная когда пишут все камеры
  зала, нажатие переключает, `pending` до подтверждения. Правила `.gbtn` удалены.
  🔴 **Красное состояние повешено на `.grp.rec .grp-recbtn`, а НЕ на `.grp.rec .rec-btn`:**
  карточки лежат внутри той же группы, и общий селектор перекрасил бы заодно кнопки REC у всех
  камер зала.
  **У свёрнутой группы кнопка прячется и остаётся прежний маленький индикатор** — решение
  владельца: кнопки там нет, а понимать, пишет зал или нет, надо.
- Счётчик и крестик держит справа распорка `.grp-gap` (`flex:1 1 0`). Именно распорка, а не
  `margin-left:auto` у счётчика: авто-отступ забирает весь остаток строки и ужаться не может — в
  узкой группе крестику не хватало места и он уезжал на вторую строку (шапка росла с 28 до 53 px).

### 21.6 В копилку §10 (методология)

- **Формулу, которой нужно делить на ширину элемента, в CSS не выразить.** `min(100%, …)` выглядит
  как ограничение, но не знает, сколько колонок влезло, — отсюда пустая полоса в 21.2.
- **`resize` — ненадёжный источник события об изменении вьюпорта.** `matchMedia`/`ResizeObserver`
  приходят там, где `resize` молчит.
- **Порядок объявлений в одном большом `<script>` имеет значение.** Блок ориентации стоял выше
  `const groupsWrap`, и добавленный в него вызов `sizeGroups()` уронил всю панель при загрузке
  (`Cannot access 'groupsWrap' before initialization` — `const` в TDZ, `if(!groupsWrap)` не
  спасает, обращение само бросает). Групп не было вообще. Объявления переставлены выше блока.
- **Проверять «ничего не изменилось» так же важно, как «изменилось».** `placeCards` зовётся на
  каждый опрос; перекладка узла роняет фокус из раскрытого селектора и рвёт начатое
  перетаскивание. Поэтому `orderBody` сначала сверяет порядок и молчит, если он верный
  (замер: 4 опроса подряд — 0 перестановок в DOM).
- **Замер в браузере врёт, если не думать о том, что меряешь.** Три случая за один заход:
  цвет читался посреди `transition:.15s` и выглядел перевёрнутым; ссылка на `.grp-body`
  протухала после `renderGroups` и показывала пустую группу; панель в **фоновой вкладке**
  отставала от сервера, потому что Chrome душит таймеры в скрытых вкладках.

### 21.7 Что проверено и чем

Живых камер под рукой не было (единственная ZV-E1 ждала связывания), поэтому проверка шла на
**подставном сервере — `tools/fakecams.py`, см. 21.9**: настоящая панель плюс придуманный парк из
семи камер обеих марок.

| Что | Результат |
|---|---|
| Автоопределение | 1440×900 и 1800×1000 → гориз; 390×844, 1080×1920 (вертикальный монитор), 440×900 (док OBS) → верт |
| Смена размера в «авто» | перестраивается без перезагрузки |
| Ручной выбор | переживает перезагрузку, автоопределение больше не вмешивается |
| Ширина групп, 1440 | 3 камеры — 1220, 2 — 817, пусто — 414, «Без группы» с одной — 392; пустого места справа ≤ 1 px |
| Ширина групп, 1024 / 1800 | 4 камеры: 817 (2 в ряд) / 1623 (4 в ряд) — переносится ровно тогда, когда надо |
| Гориз на 360 px | без горизонтальной прокрутки, грид схлопывается в одну колонку |
| Перестановка | точка вставки — 5 проб в горизонтали и 3 в вертикали, все верны; порядок доезжает до сервера и переживает перезагрузку |
| Обработчики перетаскивания | прогнаны настоящими `DragEvent` с живым `DataTransfer`: класс, метка, перестановка, уборка |
| Мигание | перетаскивание и добавление зала — 0 перезапущенных анимаций, 0 карточек стало `fresh`, 0 пересобранных залов при перетаскивании |
| Поле имени | «Зал» — 44 px, «Малый зал» — 89, 40 символов — 310; текст нигде не обрезан |
| Кнопка REC зала | покой зелёная, запись красная (текст, рамка, точка); кнопка карточки **внутри** пишущего зала остаётся зелёной |
| Свёрнутый зал | кнопка спрятана, индикатор виден и горит |
| Вертикальный режим | не изменился — все группы по 392 px, порядок и вид прежние |

⚠️ **Чего проверить не удалось:** перетаскивания настоящей мышью. Инструмент шлёт события мыши,
а Chrome для HTML5 drag-and-drop заводит собственную сессию, которая от них не запускается.
Обработчики прогнаны синтетическими `DragEvent`, но нативная часть браузера не подтверждена.
`dragstart` и обвязка при этом не менялись — только тела обработчиков.

⚠️ **Панель лежит внутри `.app`-бандла, и копирование файла туда ломает подпись** (`a sealed
resource is missing or invalid`). Порядок такой: остановить программу → положить панель →
`codesign --force --deep --sign -` → запустить. Для `build-mac` то же делает штатный `POST_BUILD`,
но он срабатывает только при перелинковке — если менялась лишь панель, надо удалить бинарник и
собрать заново.

### 21.8 Что осталось по этой теме

- **Собрать под Windows** — там панель тоже обновится (она общая), но проверить раскладку на
  реальном доке OBS стоит: именно узкий док — главный потребитель вертикального режима.
- `addGroup` / `removeGroup` по-прежнему пересобирают рамки залов целиком. Карточки при этом уже
  не перепроявляются, но если и эта перерисовка будет мозолить — `renderGroups` можно сделать
  точечным, добавляющим и удаляющим только тронутый зал.
- В узкой группе имя на все 40 символов уводит кнопку REC и счётчик на вторую строку: 310 px
  имени и органы управления в 392 px рядом не помещаются. Пока признано допустимым — обрезать
  имя хуже.

### 21.9 `tools/fakecams.py` — подставной сервер для примерки панели

Панель правится куда чаще, чем под рукой оказывается студия с живыми камерами, а половина её
поведения — группы, ориентация, ширина коробок, перетаскивание, конструктор карточки — камер и
не требует. Скрипт отдаёт **настоящую** панель из `build/Release/www` и придуманный парк из семи
камер обеих марок.

```
python3 tools/fakecams.py            # и открыть http://127.0.0.1:8799/
python3 tools/fakecams.py --port 9000
python3 tools/fakecams.py --reset    # забыть придуманные залы и раскладку
```

- **Настоящему SignalBox не мешает:** тот слушает 8787, этот — 8799. Можно держать оба.
- **Данные студии не трогает вовсе.** Придуманные залы и раскладка лежат во временной папке
  (`$TMPDIR/signalbox-fakecams`), а не в `plat::dataDir()` и не в репозитории.
- Слушает `0.0.0.0` — чтобы открыть с телефона и посмотреть, как панель сама выбирает
  вертикальную раскладку.
- **Что живое:** REC (по камере и по залу) и регуляторы меняют состояние, панель видит это
  следующим опросом; залы и раскладка карточки сохраняются; Live Preview показывает бегущие
  цветные полосы с рамкой автофокуса; у PYXIS тикает таймкод, при записи идёт счётчик и
  расходуются карта с батареей.
- **Парк подобран так, чтобы разом было видно всё:** зал, где карточки переносятся на вторую
  строку; зал на две камеры; пустой зал; камера без зала. Плюс состояния, которые вживую поймать
  трудно: запись, севшая батарея, перегрев, tally Program и Preview, питание от аккумулятора.
- Значения взяты из образцов самой панели (`SAMPLE_SONY` / `SAMPLE_BMD` — те же, что показывает
  конструктор карточки), поэтому правило «ничего не выдумывать» (§10.0.1) не нарушено: здесь
  ничем не управляют и ни за какие показания себя не выдают.

🔴 **Чего он НЕ заменяет.** Это макет интерфейса, а не эмулятор камер: ни Sony SDK, ни REST
Blackmagic за ним нет. Всё, что касается общения с железом — связывание, `0x820A`, реальные
задержки применения, поведение при пропаже камеры — проверяется только на живых камерах.
